## 1. プロダクト概要

- **目的**: B.LEAGUE（https://www.bleague.jp/）の個人専用スタッツサイトを作る
- **優先カテゴリ**: B.PREMIER（最優先。B.ONE / B.NEXTは当面対象外）
- **対象シーズン**:
  - 最優先: 2026-27シーズン（2026年10月開幕）を全試合カバー
  - 過去データ: 理想は2016-17シーズン（B.LEAGUE発足）以降の全シーズン。
    実装難易度が高い場合は「直近3シーズン」まで縮小可、それも厳しければ
    「新シーズンのみ」でリリースし、過去データは後日バックフィルする
  - 注意: ショットチャート等一部の可視化データは公式サイト上でも2022-23シーズン以降にしか
    存在しない可能性が高い。過去シーズンは機能によって対応範囲が変わることを許容する
- **提供形式**: チームスタッツ／個人スタッツ／試合詳細／順位表　それぞれ一覧＋詳細
- **利用者**: 開発者本人のみ（外部公開は前提としない。閲覧認証は不要）
- **関連プロジェクト**: 既存のブレックス観戦カレンダーPWA（Firebase + GitHub Pages）
  とは**別リポジトリ・別プロジェクト**として新規に作成する（技術スタックの知見は流用可）

## 2. データソースと制約

B.LEAGUE公式サイトに一般公開APIは無いため、公式サイトのHTML／内部データをスクレイピングして
取得する。`game_detail` ページの調査により、公式サイトには以下のセクションが既に存在することを
確認済み（＝該当データは公式に公開されている）。

| 用途 | URL例 / セクション | 備考 |
|---|---|---|
| 試合スケジュール一覧 | `https://www.bleague.jp/schedule/?data_format=json&year=...&mon=...&day=...&event=...` | HTMLではなくAJAX用のJSON APIが存在することを確認済み（2-2章）。ScheduleKey一覧をHTMLパース不要で取得可能 |
| ボックススコア | `https://www.bleague.jp/game_detail/?ScheduleKey=XXXXXX&tab=2` | 選手別・チーム別の基本スタッツ。Q別得点・スタメン表記も含まれる想定 |
| ゲームリーダー | 同ページ内セクション「ゲームリーダー」 | チーム別スタッツ上位者。box scoreから自前集計でも代替可 |
| スコアチャート | 同ページ内セクション「スコアチャート」 | JS描画。裏にAPI/JSONがある可能性が高く、**実装着手時に最優先で調査**（Lead Tracker実現の鍵） |
| ゲームスコア／試合成績 | 同ページ内セクション「ゲームスコア」「試合成績」 | JS描画（今回のfetchでは値が"--"表示で内容未確認）。Fastbreak Points・Points In Paint・Bench Points・eFG%等、詳細なチーム比較スタッツが含まれている可能性が高い。**スコアチャートと同様に最優先で裏側データを調査**（12章のチームスタッツ項目カタログの多くがここに依存） |
| ショットチャート | 同ページ内セクション「ショットチャート」 | 2022-23シーズン以降のみ存在（それ以前は無い想定） |
| テキスト速報 | タブ「テキスト速報」 | 得点・タイムアウト・選手交代等の時系列イベントログの可能性。Lead Tracker/交代バー/ラインナップスタッツの代替データ源 |
| 選手・チーム個別ページ | `https://www.bleague.jp/roster/` 配下の選手詳細ページ | 国籍・登録区分（日本人/外国籍/帰化/アジア特別枠）、身長・体重・生年月日等のプロフィール情報 |
| 成績詳細（検証用） | `https://www.bleague.jp/stats/` | 自作集計値の突合・検証に使える |
| 順位表（シーズン一覧の確認） | `https://www.bleague.jp/standings/` | シーズンプルダウンが 2016-17〜2026-27 まで存在することを確認済み |

### 2-1. 試合詳細データの裏側API（検証済み・Phase 1はこの方式で進行）

`game_detail` ページが読み込む `genius_game_new2208.js` のソースに、ボックススコア・
プレイバイプレイ・Q別得点等を配信するJSON APIのURLパターンが書かれていることを発見し、
**Claude Codeによる実機検証で実際に取得できることを確認済み**。HTMLスクレイピングではなく
**このJSON APIを直接叩く方式でPhase 1を進める**（詳細は2-2章の検証結果を参照）。

**確認できたURLパターン**（`_contexts.scheduleKey` は対象試合の `ScheduleKey`）:
```
1. http://b-league.s3.amazonaws.com/web_json/v2_genius_contexts/{ScheduleKey}/latestid
   → その試合の最新リビジョンID（整数）を返す
2. http://b-league.s3.amazonaws.com/web_json/v2_genius_contexts/{ScheduleKey}/{latestid}.json
   → 試合の全データ（Game / PlayByPlays / HomeBoxscores / AwayBoxscores / Summaries）
```
コード中には `dev-bleague.s3.amazonaws.com`（検証用）という変種も存在したが、**Claude Codeの実機
検証により、どちらか一方が実際に有効であることを確認済み**（詳細は2-2章）。
なお、B3の試合は `v1_contexts` という別パスを使っている形跡があり（B.PREMIER優先の本プロジェクトでは
直接関係しないが留意）、ショットチャートと同様にこの仕組みは**2022-23シーズン以降のみ**対応している
可能性が高い（box scoreのヘッダー描画ロジックが `game_year >= 2022` で分岐している）。過去シーズンの
バックフィル時に別途確認が必要。

**確認できたJSONのフィールド名（ソースコードの参照箇所から）**:
- `Game`: `GameDateTime`, `GameCurrentPeriod`, `MaxPeriod`, `HomeTeamScore`, `AwayTeamScore`,
  `HomeTeamScore01`〜`14`/`AwayTeamScore01`〜`14`（Q別・OT別得点）, `GameEndedFlg`, `RecordFixedFlg`
  （← **8章で設計した「試合確定/修正監視」のstatus判定にそのまま使える**）, `ConventionKey`,
  `ConventionNameJ`, `Attendance`, `RefereeNameJ`, `SubRefereeNameJ1/2`, `HomeTeamID`, `AwayTeamID`,
  `PlayByPlayExistsFlg`, `BoxscoreExistsFlg`
- `PlayByPlays[]`: `Period`, `ActionCD1`（イベント種別コード）, `RestTime`（残り時間）, `PeriodEndRowFlg`
- `HomeBoxscores[]` / `AwayBoxscores[]`: `PeriodCategory`（1〜4=各Q、18=試合全体。**Qごとのボックス
  スコアがそのまま取れる**）, `PT2M`/`PT2A`, `PT3M`/`PT3A`, `FTM`/`FTA`, `FG%`/`2FG%`/`3FG%`/`FT%`,
  `TR`, `Category`（選手行かチーム合計行かの区別）
- `Summaries`: シーズン平均の比較データ（ヘッダーのPPG/FG%等の元）

**`ActionCD1`（プレイバイプレイのイベント種別コード）の対応表（アイコン割り当てから逆算）**:
| コード | 意味 |
|---|---|
| 1 | 3P成功 |
| 3, 4 | 2P成功 |
| 7 | フリースロー成功 |
| 15, 20〜26, 46 | ファウル |
| 86, 87, 89 | 選手交代（イン/アウト） |
| 88, 90 | タイムアウト |

**選手交代・タイムアウトのコードは確定済み**（2026年8月13日、`genius_game_new2208.js`の
ソースコードを直接特定・実データで裏付け。詳細は2-2章末尾）。

**この発見のインパクト**: `PlayByPlays` に**タイムアウトと選手交代がイベントコードとして明確に
記録されている**ことが分かったため、12章までは「テキスト速報の自由記述をパースする」前提だった
Lead Tracker・タイムアウトプロット・選手交代バー・ラインナップ/オンコートオフコートスタッツが、
**同一の構造化JSONから直接構築できる可能性が高い**（テキストの曖昧なパースが不要になる）。
これにより3章・12章のティア判定を以下のように更新する：
- Lead Tracker／リード時間／タイムアウトプロット：ティアB→**ほぼティアA相当**（要フィールド確認だが
  スコアチャートと同じデータ源であることが確認済み）
- 選手の出場交代バー／ラインナップスタッツ／オンコート・オフコートスタッツ：ティアCのままだが、
  「テキスト解析による精度リスク」から「構造化イベントデータのパース精度検証」に性質が変わり、
  リスクは大きく下がった（選手ID/チームIDが各イベントにどう紐付くかは要確認）

### 2-2. 検証結果（確定・6試合4,513件のPlayByPlaysで検証済み）

Claude Codeによる複数試合サンプルでの実機検証が完了。以下は確定情報として扱ってよい。

**OT（延長戦）の扱い**:
- `HomeTeamScore05`/`AwayTeamScore05` はOT発生時のみ動的に追加される（通常試合には存在しない）
- `MaxPeriod` は延長でも `4` のまま変わらない（レギュレーションQ数の固定値）。延長判定には
  `GameCurrentPeriod=5` かScoreフィールドの存在数を見る必要がある
- `PeriodCategory` はOT試合で `5`（OT本体）・`17`（延長合計）が追加される。1OTのみの試合では
  この2つの値が完全一致することを確認済み。**複数OT時の挙動は未検証**（プレーオフ等でOTが
  2回以上続いた試合があれば追加確認が望ましい。低頻度の事象なので実装のブロッカーではない）

**`Category` の意味（5試合で比較し確定）**:
- `Category=1` ＝ 個人選手行
- `Category=2` ＝ 個人に紐付かないチーム発生イベント行（チームリバウンド／チームターンオーバー
  のみ非ゼロ）
- `Category=3` ＝ 真のチーム合計行（`PlayTime`が200:00＝40分×5人、`Point`が最終スコアと一致）
  → **チームスタッツの集計はこの行を正として使うのが最も簡単で確実**

**`ActionCD1` の全体像（6試合・4,513件を走査し32種類を確定）**:
3P/2Pの成功・失敗の細分化、パーソナル/オフェンス/アンスポーツマンファウルの区別など、当初の
推測表よりかなり詳細なことが判明。`20, 21, 24, 26, 46, 89, 90`（テクニカルファウル等と推測）は
今回未出現。**運用方針**: 未知のコードが来たらエラーにせずログに記録して集計は継続する
（8章の差分検知の仕組みと同様、「知らないデータに遭遇したら気づけるようにする」設計にする）。

✅ **解決済み（2026年8月13日）**: 未出現だった `89`・`90` を含む選手交代・タイムアウトの
`ActionCD1`コードは、観測に頼らず`genius_game_new2208.js`のソースコード（`EventIcons`
オブジェクトのアイコン割り当てロジック）を直接読むことで確定した。加えて4試合・3,043イベントの
実データで`PlayText`（`"プレイヤーイン"` `"プレイヤーアウト"` `"タイムアウト"`）による裏付けも
取れている。詳細・確定表は2-2章末尾を参照。Lead Tracker・選手交代バー・ラインナップスタッツ
（ティアB/C）着手のブロッカーは解消。

**副産物の発見（想定より楽観的な方向に更新）**:
- `Summaries` に **Fastbreak Points / Points In Paint / Second Chance Points が直接含まれている**
  → 12章「プレータイプ内訳」はテキスト速報頼みの想定が外れ、**ティアA相当に格上げ**
- PlayByPlaysのシュートイベントに **`X`/`Y`/`AreaCD`（座標）が同梱** → ショットチャートも
  同一APIで完結する見込み（ただし2022-23シーズン以降のみという season制約は別途残る）

検証用スクリプトは `scripts/` 配下に保存済み。上記を踏まえ、**Phase 1のスクレイパー本実装
（`scrape-boxscore.ts` 等）に進んでよい**。

### 2-4. 選手交代・タイムアウトのActionCD1コード確定（2026年8月13日）

11章で積み残していた「選手交代・タイムアウトのActionCD1コードが未観測」という課題を解決。
観測に頼る方式（多くの試合を集めてコード出現頻度から逆引きする）ではなく、`game_detail`ページが
読み込む`genius_game_new2208.js`（実際のURL: `https://bleague.bl.kuroco-img.app/v={hash}/files/js/front/user/genius_game_new2208.js`。
`{hash}`はキャッシュバスティング用のバージョン番号でデプロイのたびに変わる。`game_detail`ページの
`<script src>`から都度取得するのが確実）のソースコードを直接読み、アイコン割り当てロジック
`EventIcons`オブジェクトからコードを特定した：

```js
var EventIcons = {
    "1": 3, "3": 2, "4": 2, "7": 1,
    "15": ".../icon-f.svg", "20": ".../icon-f.svg", ..., "46": ".../icon-f.svg",
    "86": ".../icon-inout.svg",
    "87": ".../icon-inout.svg",
    "88": ".../icon-t.svg",
    "89": ".../icon-inout.svg",
    "90": ".../icon-t.svg"
};
```

**確定した対応（以前の推測表と完全一致）**:
| コード | 意味 | 実データでの裏付け |
|---|---|---|
| 86 | 選手交代・イン | `PlayText: "#5 テリー プレイヤーイン"`（4試合中70/88/71/76回観測） |
| 87 | 選手交代・アウト | `PlayText: "#13 津山 プレイヤーアウト"`（4試合中60/78/61/66回観測） |
| 89 | 選手交代関連（未観測） | ソース上は86/87と同一`icon-inout.svg`を割当。4試合には未出現だが、割当ロジック自体は確定 |
| 88 | タイムアウト | `PlayText: "タイムアウト"`。`HomeAway`が数値＝通常のチームタイムアウト、
  `HomeAway === null`のときはソース側で「オフィシャルタイムアウト」表記に切り替わる（4試合中9〜11回観測） |
| 90 | タイムアウト関連（未観測） | ソース上は88と同一`icon-t.svg`を割当。ただしソース内に
  `ActionCD1 == 90`のときだけ`PlayText`に「タイムアウト」を追記する専用分岐があり、
  88とは何らかの形で区別されている（オフィシャルタイムアウトとは別の値であるため、
  ビデオチャレンジ関連等の可能性はあるが未確認。低頻度事象と推測され、実装のブロッカーではない） |

**選手交代イベントの構造**: 1イベント＝1選手（`PlayerID1`/`PlayerNameJ1`/`PlayerNo1`）で、
IN・OUTはそれぞれ独立した行として記録される（1つのイベントにIN/OUT両方の選手情報が同梱される
構造ではない）。ラインナップ復元時は、同時刻・同チームのIN行とOUT行をペアリングする実装が必要。

**検証方法**: `data/2025-26/games/*.json`（4試合・PlayByPlays計3,043件）を集計し、86・87・88の
出現回数が試合として妥当な範囲（1試合あたり交代60〜100件強、タイムアウト9〜11件）であることを
確認。89・90は今回のサンプルには出現しなかったが、観測頼みではなくソースの割当ロジック自体を
直接確認したため、確定情報として扱ってよい。

### 2-5. Lead Tracker実装（2026年8月13日）

得失点差の推移をグラフ化する「Lead Tracker」を実装。データソースは新規のバックエンド集計を
追加せず、既に`games/{scheduleKey}.json`に保存済みのPlayByPlaysをフロントエンドでその場整形する
方式を採用（`src/lib/leadTracker.ts`）。

**時間軸の作り方**: PlayByPlaysの`RestTime`（そのピリオドの残り時間）を「試合開始からの累計経過秒」
に変換する。ピリオドの秒数はB.LEAGUE公式ルール通り各Q10分・延長(OT)5分固定とし、実データ
（延長開始行の`RestTime`が"5:00"であること）でも裏付け済み。公式サイトのスコアチャート実装
（`PBPGraphBuilder`）は各ピリオドを固定幅の列に押し込めて表示する方式（延長も見た目上は他Qと
同じ幅になるよう時間を2倍スケールする専用ロジックがある）だが、本実装は「Q跨ぎを含めた連続した
経過時間」を軸にしたかったため、この実際の経過秒をそのままX軸に使う独自方式にした（結果として
延長Qは他のQより視覚的に幅が狭く表示され、実際の試合時間の長さの違いが直感的にわかる）。

**得点イベントの特定**: 得点が入るActionCD1コード（1, 3, 4, 7, 44）は、公式サイトのスコアチャート
実装（`PBPGraphBuilder.update`内の`pointsHashTable`）と同じ値を採用。各イベントの`Score`フィールドに
その時点の両チーム累計スコアがそのまま入っているため、得点計算をこちら側で再現する必要はなく、
そのままstep chart（`recharts`の`type="stepAfter"`）のデータ点として使える。

**タイムアウトのマーキング**: 2-4章で確定したActionCD1=88のイベントを、対応する経過秒の位置に
縦の点線（`ReferenceLine`）で表示。`HomeAway`でホーム/アウェイ/オフィシャルタイムアウトを色分け。

**Y軸（得失点差）**: ホームチーム視点の得失点差（ホーム−アウェイ）を、0を必ず跨ぐよう
`[-halfRange, halfRange]`の対称なドメインで表示。0より上をホームチームカラー、0より下をアウェイ
チームカラーで塗り分ける（`linearGradient`のオフセットをドメイン中央=50%に固定することで実現。
対称ドメインなので常に50%になる）。

**画像出力ボタンは非搭載**: 6章で確認済みの制約（html2canvasがrechartsのSVGグラフを正しく
描画できない）に該当するため、他のスタッツランキング等と異なり画像出力ボタンは付けていない。

**動作確認**: 延長なし（ScheduleKey 506099）・延長あり（ScheduleKey 505288）の両方で実データ描画・
ツールチップ表示・コンソールエラー無しを確認済み。505288はOT区間が他のQより狭い幅で正しく
表示されることも確認した。

### 2-6. 在コート状態の復元・精度検証（Phase 4基盤、2026年8月13日）

ラインナップスタッツ／オンコート・オフコートスタッツ（ティアC）の前提となる「PlayByPlaysから
各時点の在コート5人を復元する」ロジックを`shared/onCourt.ts`に実装し、`scripts/validate-oncourt.ts`
（`npm run validate:oncourt`）で精度検証した。**UIには一切組み込んでいない**（検証専用）。

**復元ロジックの要点**:
- 在コートの初期状態はBoxscoreRowの`StartingFlg`では初期化しない。実データを見ると試合開始時点
  （Period1・RestTime10:00）にスタメン5人×2チーム分のActionCD1=86（IN）イベントが明示的に
  記録されていることを確認したため、PBP自体から復元する（BoxscoreRowの`StartingFlg`は
  復元後の突合検証にのみ使う。詳細は下記「判明した問題」参照）
- 得点イベント（ActionCD1: 1, 3, 4, 7, 44。Lead Trackerと同じ公式`pointsHashTable`）のたびに、
  その時点で在コートの選手全員に得失点を加減算し、個人+/-を再計算する
- 選手交代イベント（86=IN, 87=OUT）を同一秒・同一チームでバッチ処理し、バッチ適用後に
  在コート人数が5人になっているかを確認する

**検証結果（4試合・PlayByPlays計3,043件、うちOT2試合）**:
| 検証項目 | 結果 |
|---|---|
| 在コート人数（常に5人か） | 崩れ0件 |
| 選手ごとの在コート時間 vs 公式MIN（±6秒許容） | 85/85人（出場選手全員） = 100% |
| 復元+/- vs 公式PLUSMINUSフィールドの完全一致 | 96/96人（DNP含む全選手） = 100% |

**開発中に発見した2つの問題と対応**:
1. **PlayByPlays配列は必ずしも試合内の時系列順ではない**: ある試合（ScheduleKey 505118）で、
   配列の途中（本来は延長(Period5)の区間）に、通常であればもっと前にあるはずのPeriod1の
   一連のイベントが丸ごと挿入されているのを発見した（恐らく後日の記録修正が反映されたタイミングで
   配列に追記されたことによるものと推測。8章で触れている「試合終了後の記録修正」がPBPレベルでも
   起きている証拠）。対策として、`RestTime`から試合開始からの累計経過秒(elapsedSec)を算出し、
   **配列の並び順ではなくelapsedSecの昇順で全イベントをソートしてから**処理する設計にした
2. **同一秒内のイベント順序を独自ルールで決め打ちすると個人+/-がズレる**: `RestTime`の解像度は
   1秒しかないため、「交代→フリースロー→交代」のように同じ1秒間に複数のイベントが起きるケースが
   ある（シュートファウルの反則直後に交代し、その後フリースローを打つ、等）。当初は「同一秒内は
   得点イベントを交代イベントより先に処理する」という決め打ちルールにしていたが、これだと
   フリースロー**前**に行われた交代（新しく入った選手がフリースローの結果を受け取るべきケース）を
   誤って逆順に処理してしまい、公式PLUSMINUSとズレる原因になっていた。実データを調査した結果、
   **同一秒内では配列に記録された元の並び順が実際の発生順と一致している**ことを確認できたため
   （JavaScriptの`Array.sort`は安定ソートである性質を利用し、elapsedSecが同値の場合は
   独自の優先順位を付けず元の配列順序をそのまま保持する設計に修正）、この問題を解消した。
   修正前は+/-完全一致率が47.9%（46/96人）だったが、修正後は100%になった

**結論・次のステップへの示唆**: MIN一致率100%・+/-完全一致率100%という結果は、在コート復元
ロジックの信頼性が非常に高いことを示している。この基盤の上に、ラインナップスタッツ（5人組み合わせ
ごとのオン/オフコートスタッツ）を実装する判断材料として十分な精度と言える。ただし今回の検証は
サンプルが4試合（うちOT2試合）のみのため、2026-27シーズンが本格的に始まり試合数が増えた際に、
同じ検証（`npm run validate:oncourt`）を再実行して結果が崩れないか確認することが望ましい。

### 2-8. チーム名変更履歴とTeamIDの安定性調査（2026年8月13日）

バックフィル実装（3層スクレイパー）の前提として、改称したクラブでも`TeamID`が不変かどうかを
実データで検証した。結論: **`TeamID`はクラブ改称をまたいで不変**。バックフィル時にチーム名の
文字列一致に頼る必要はなく、`TeamID`だけで安全にシーズンをまたいだ名寄せができる。

**検証方法**: `bleague.jp/stats/`（成績詳細ページ）のクラブ絞り込みプルダウンは、選択した
シーズンに応じて当時のクラブ名を表示するが、`<option>`の`value`属性（=`TeamID`）はbleague.jp
の内部システムが持つ恒久的なクラブIDであり、シーズンをまたいでも同じ値を保持している。これを
複数シーズンで比較し、さらに実際のgenius_contexts APIレスポンスでも裏取りした。

**確認できた実例**:
- **栃木ブレックス → 宇都宮ブレックス**（2019年7月改称、2019-20シーズン〜適用）: 2016-17
  シーズンのプルダウンでは「栃木」(`value="703"`)、2020-21シーズン以降のプルダウンでは「宇都宮」
  (`value="703"`)。**同一TeamID**。genius_contexts APIは2016-17時点が403で直接検証はできないが、
  bleague.jpの内部クラブIDが不変であることは確認できた
- **サンロッカーズ渋谷 → 東京サンロッカーズ**（2026-27シーズン〜改称予定・発表済み）: 2020-21

### 2-3. 実装中に判明した追加事項

- **スケジュール一覧のJSON API発見**: `bleague.jp/schedule/` は通常のfetchでは空になるが、
  実際は `?data_format=json&year=...&mon=...&day=...&event=...` というAJAX用JSON APIが
  裏にあり、これで `ScheduleKey` 一覧をHTMLパース不要で取得できることを確認（2章の表に反映済み）
- **`PlayingFlg` の解釈ミスを修正**: 得点・出場時間が記録されている選手でも `PlayingFlg=false`
  になるケースがあった。出場判定は `PlayingFlg` ではなく **`PlayTime !== "DNP"`** で行う

なお「試合成績」セクションには「もっと詳しく見る」リンクがあるが、別リクエストは観測されなかった
ため、**既に取得済みの同一JSON内に追加フィールド（Fastbreak Points等）が含まれ、クリックで表示を
切り替えているだけ**の可能性が高い。12章のプレータイプ内訳スタッツもこのJSON内で解決する可能性がある。

**制約・注意点**（自動更新・無料の要件を守るために厳守）:
- 個人利用の範囲に留める。取得データを再配布・商用利用しない
- リクエスト間隔は最低2〜3秒空ける（サーバー負荷対策）。並列アクセスしない
- 過去シーズン（特に2016-17〜2019-20あたり）はサイトリニューアルでHTML構造が異なる可能性が高い
- サイト構造は将来変わりうるため、スクレイパーはセレクタを1箇所にまとめ、壊れたときに検知・修正しやすい構成にする
- 「スコアチャート」「テキスト速報」は実装前に**必ず実データ（ネットワークリクエスト／HTML構造）を調査**し、
  構造化データとして取得できるか、それとも自前でテキストパースする必要があるかを確認してから設計を確定する
- **試合終了直後のボックススコアは確定値ではない**。公式記録は試合後に修正（誤記訂正・スコアラー修正等）
  が入ることがあり、経験上**試合終了から約1週間後に数値が修正されるケースがある**。「1回取得して終わり」
  ではなく、**直近の試合を一定期間繰り返し再取得し、差分があれば上書きする**仕組みが必須（詳細は8章）

## 3. 機能要件と実現性ティア

要望を実現性で3ティアに分類。ティアA/Bは公式サイトのデータをほぼそのまま使えば実現でき、
ティアCは公式サイトに直接の該当機能が無く、テキスト速報等から**自前で再構成**する必要がある
（実装してみて精度が低ければ縮小・撤退する前提で着手：ユーザーとの合意事項）。

### ティアA：確実に実現可能（ボックススコアの集計のみで完結）
- 各Q終了時点の両チームの得点
- 各スタッツの上位3人（チーム別・ゲームリーダー相当）
- キースタッツのビジュアライザ
- スタート5人／ベンチ出場選手それぞれのスタッツ
- スタッツ画像の出力（全ページ共通機能）
- チーム／個人の比較、シチュエーション別スタッツ（時期別・勝敗別・直近◯試合）
- Netスタッツ（自チーム−相手チーム）、スタッツランキング一覧、ランキング画像出力、勝敗傾向
- チーム別ページ（シーズン成績・個人スタッツ・勝敗傾向・スタッツリーダー）
- 個人ページ（シーズン成績・試合ごとのログ・通算成績）
- 順位表（順位遷移・勝ち星推移・貯金推移・星取り表）

### ティアB：追加のデータ整備で実現可能
- ✅ **実装済み（2026年8月13日）**: Lead Tracker表示・タイムアウトのプロット
  → スコアチャートの裏APIは使わず、既に保存済みのPlayByPlays（`games/{scheduleKey}.json`）から
  フロントエンドでその場構築する方式で実現（詳細は2-5章）
- 日本人／外国籍／帰化・アジア特別枠選手それぞれのスタッツ
  → 選手マスタ（国籍・登録区分）を roster ページから整備し、box scoreの選手と突合
- スタメン選手の平均身長・年齢・体重
  → 同じ選手マスタ（プロフィール情報）を利用
- マジックナンバー計算表
  → B.PREMIER新フォーマットの昇降格・プレーオフ進出ルールを確認してから実装（2026-27再編のため要確認）
- 個人スタッツランキングの国籍区分フィルタ（**日本人選手ランキング**等）
  → 上記の選手マスタが前提。マスタが整備できればランキング機能自体はtier A相当のロジックで実現可能
- ユーザーがこれまで運用してきたチームスタッツ項目一式（Fastbreak Points・Points In Paint等の
  プレータイプ内訳、ペイント内外シュート、デッド/ライブターンオーバー等）
  → 詳細は **12章「チームスタッツ項目カタログ」** を参照。項目ごとに依存データが異なるため個別にティア分け

### ティアC：実現は可能だが難易度・精度リスクが高い（試験実装として後半フェーズに投入）
- 選手の出場交代のバー表示
- ラインナップごとのスタッツ
- オンコート／オフコートスタッツ

→ いずれも「10人の選手が試合中いつコートに立っていたか」を秒単位で追跡する必要があり、
テキスト速報の選手交代記録の網羅性に精度が依存する。実装後、各クォーターの在コート合計時間が
ボックススコアのMIN（出場時間）と一致するかで精度を検証し、**閾値を満たさない場合は機能を
非表示にするか「参考値」として注意書き付きで出す**、という前提で進める（ユーザー合意済み）。

✅ **基盤の精度検証は完了（2026年8月13日、2-6章）**: 在コート状態の復元ロジック
（`shared/onCourt.ts`）を実装し、手持ちの4試合全件でMIN一致率100%・個人+/-の公式値との
完全一致率100%を達成。

✅ **出場交代バー表示は実装済み（2026年8月13日）**: `shared/onCourt.ts`の`reconstructOnCourt`を
使い、`GameDetailPage.tsx`にLead Trackerと同じ画面内で選手ごとの在コート区間をガントチャート状に
表示（`src/components/SubstitutionBarChart.tsx`）。スタメン/ベンチ別・ボックススコアと同じ並び順、
Lead Trackerと同じperiodBoundaries/totalSecondsを共有して時間軸を揃えている（選手名ラベル分の
ガター幅が異なるため厳密なピクセル単位の一致ではないが、Q区切り線・ラベルは共通なので対応関係は
十分に見て取れる）。複数区間を持つ選手を表現する必要があり`recharts`のBar系コンポーネントでは
表現しづらいため、CSS(flexレイアウト＋絶対配置)で自前実装した。506099（延長無し）・505288（OT）
両方で実データ表示を確認済み。ラインナップスタッツは次フェーズ。

✅ **オンコート/オフコートスタッツ（個人）は実装済み（2026年8月13日）**: 個人+/-（公式
`PLUSMINUS`フィールド）は定義上すでに「オンコート純得失点」そのものであるため、`shared/onCourt.ts`
によるPBP再走査は不要と判明（ユーザー指摘）。`scripts/aggregate.ts`で、選手が出場した各試合の
「チーム得失点差」を`teamNetSum`として積算し、`オフコート純得失点 = teamNetSum − 個人+/-合計`
という単純な差分で導出した（シーズン合計・1試合あたり平均の両方をplayers.jsonの`advanced`に追加）。
`src/lib/statDefs.ts`に`onCourtNet`/`offCourtNet`を追加（`source: 'custom'`）。ただし今回のスコープは
個人詳細ページでの確認のみのため、`StatMeta`に`hiddenFromPicker`フラグを新設し、ランキング・比較
ページの選択肢からは除外しつつ用語集には掲載する形にした（RankingsPage/ComparePageは
`PLAYER_STAT_DEFS.filter(d => !d.hiddenFromPicker)`で参照）。

**検証**: 単一試合のみ出場した選手（須藤タイレル拓、チーム最終スコア差-6）でオンコート+13/
オフコート-19（合計-6と一致）、複数試合出場の選手（ドゥシャン・リスティッチ、3試合）でチーム得失点差
合計(-9+9+6=6)からオンコート純得失点15を引いた値がオフコート-9と一致することを手計算で確認。
season全選手のオンコート純得失点合計と個人+/-合計が一致することも確認済み（定義上必然だが実装ミス
がないことの確認として実施）。

✅ **ラインナップスタッツは実装済み（2026年8月13日）**: `shared/onCourt.ts`の`reconstructOnCourt`を
拡張し、個人+/-と全く同じイベント順（tie-break無し・配列の元の並び順を信頼する方式）で、同じ5人が
同時に在コートだった区間を「スティント」として同時に積算するようにした（`LineupStint`型・
`OnCourtReconstruction.lineupStints`）。5人の組み合わせはplayerIdをソートして`,`結合した
`lineupKey`で正規化し、順不同でも同一視する。`scripts/aggregate.ts`の`processLineups()`で
シーズン全試合分をチーム別・lineupKey別に積算し、`data/{season}/lineups/{teamId}.json`に出力する。

**検証**（`scripts/validate-oncourt.ts`を拡張、手持ち4試合＝チーム×試合で8ケース）:
1試合内の「あるチームの全スティント時間の合計」が試合時間（40分＋OT分）と、「全スティント純得失点の
合計」がそのチームの最終得失点差と、それぞれ**8/8ケースで完全一致（100%）**。個人+/-の検証で確立済みの
イベント順ロジックをそのまま流用しているため理論的にも一致するはずだが、実データでも実証した。

**Net Rating（推定）について**: スティント単位の実ポゼッション数はデータ上取得できないため、
チームのシーズン平均ペース（`POSS / (MIN合計/5)`）からスティント時間分を按分して推定ポゼッション数を
算出し、`100 * 純得失点 / 推定ポゼッション数`として計算する近似値（`estimatedNetRtg`）。他のNBA流
アドバンスドスタッツと同様、公式に定義が無いため代替の考え方を採用した位置づけ。

**表示**: `TeamDetailPage.tsx`に「よく使われるラインナップ」セクションを追加。出場時間180秒未満の
組み合わせはサンプルが小さくノイズが大きいため除外し、出場時間の多い上位10組を試合数・出場時間・
得失点差・Net Rating（推定）とともに表示する（実データ確認: 4試合時点で180秒基準だとチームあたり
4〜14組が該当）。閾値・Net Ratingが推定値であることの注意書きをテーブル直下に表示している。
ランキング・比較ページへの追加は対象外（チームごとの個別データのため既存のstatDefs.tsの仕組みには
乗らない）。

## 4. 技術スタック

- **データ取得（スクレイパー）**: Node.js（ネイティブTypeScript実行）＋ `v2_genius_contexts` JSON API直接取得
- **データストア**: JSON静的ファイルをリポジトリにコミットする方式（DBレス、無料、シンプル）
- **フロントエンド（確定）**: **Vite + React**。ルーティングは `react-router`（GitHub Pagesでの
  デプロイのため **hashルーター**を使用。素のパスルーティングだとリロード時に404になるため）。
  チャート描画は `recharts`（Lead Tracker・ランキング・キースタッツビジュアライザ等の大半をカバー）。
  ショットチャートの座標プロットのみ`recharts`では表現しづらい場合、SVG直描画かd3を部分的に併用
- **画像出力**: `html2canvas` でDOMを画像化。**既知の制約**: rechartsのSVGバーチャートは
  html2canvasで正しく描画されない（バーがほぼ描画されない不具合を確認済み）。テーブル中心の
  画面（ランキング・比較ページ等、`color-mix()`ハイライト含む）はライブ画面と一致する画像を
  生成できることを確認済み。rechartsグラフを含む画面（試合詳細ページのKeyStatsChart等）へ
  画像出力を広げる際は、グラフ部分を`<canvas>`ベースの別ライブラリに差し替える／別のキャプチャ
  手段を使う／グラフ画面は画像出力対象外にする、のいずれかの判断が必要
- **ホスティング**: GitHub Pages
- **自動更新**: GitHub Actions の `schedule`（cron）トリガーでスクレイパーを定期実行 →
  JSON更新 → 自動コミット・push → GitHub Pagesへ自動反映

## 5. データモデル（JSON設計案）

```
data/
  2026-27/
    games/
      505076.json         # 1試合分の生データ（ボックススコア＋Q別得点＋PBP等）
      ...
    player-games/
      {playerId}.json      # 選手ごとの試合ログ（個人詳細ページ用。aggregate.tsが生成）
      ...
    team-games/
      {teamId}.json         # チームごとの試合結果一覧（チーム詳細ページ用。aggregate.tsが生成）
      ...
    teams.json             # シーズン通算のチーム別集計（基本＋アドバンスド）
    players.json           # シーズン通算の選手別集計（基本＋アドバンスド）
    standings-history.json # 日付ごとの順位スナップショット（順位遷移用）
  2025-26/
    ...
  players-master.json      # 選手プロフィール（国籍・登録区分・身長・体重・生年月日）※全シーズン共通
  seasons.json              # 収録済みシーズン一覧・メタ情報
```

**選手マスタのスクレイピング（実装済み・Phase 3）**: `bleague.jp/roster/`・`roster_detail/` を実機調査した
結果、game_detail/scheduleと違い**裏側JSON APIは存在しない**（フィルタ操作を含めて素のHTMLページが
クエリパラメータ付きで返るだけ。ネットワークログでXHR/JSON呼び出し無しを確認済み）ため、
`scrape-roster.ts` はcheerioによるHTMLスクレイピングで実装した。
- 一覧: `bleague.jp/roster/?year={year}&club={teamId}&p=&c=&o=random&e=在籍中&tab=1`
  （クラブを絞ると在籍中選手が1ページに収まる。26クラブ分回せば全選手を網羅できる。取れるのは
  playerId・氏名・ポジションのみ）
- 個人: `bleague.jp/roster_detail/?PlayerID={id}`（生年月日・身長／体重・リーグ登録国籍を取得）
- 更新方針: 一覧ページは毎回26クラブ分取得してteamId/teamName/positionを更新（軽量・移籍検知）。
  個人ページは「まだマスタに無い新規選手」だけ追加取得する（身長体重等は変化しないため）。
  これにより2回目以降の実行は新規選手が居ない限り一覧ページの26リクエストのみで完了し、
  日次cronに組み込んでも軽量（8-1章の方針と同じ考え方）。初回のみ在籍中の全選手（300名超）の
  個人ページを新規取得するため15〜20分程度かかる（日次cronに組み込む前に手動でフル実行済み）
  - **teamIdは固定値ではなく毎回上書きされる**: 個人ページを再取得しない既存選手であっても、
    `teamId`/`teamName`は日次cronが走るたびに26クラブの一覧ページ再取得から必ず上書きされる
    （`scrapeRosterMaster()`内で選手が既知でも`entry.teamId = teamId`を毎回実行）。そのため
    移籍が起きても手動更新は不要で、次の日次実行で自動的に反映される。「固定teamIdを避けたい」
    という方針に沿っている。既存選手の所属クラブが前回と変わっていた場合は`movedCount`として
    ログにも出す（移籍検知の可視化）
- **classification（日本人/外国籍/帰化選手/アジア特別枠）は自動判定＋手動上書きのハイブリッド方式
  で実装済み**: `リーグ登録国籍`欄は単一の国名のみで、帰化選手も「日本」表記になり生え抜き選手と
  区別できない（実際に確認: アジア特別枠として知られる韓国出身選手も、通常の外国籍選手と同じ形式で
  母国の国籍が表示されるだけ）。追加調査として以下も確認したが、いずれも該当データは無かった:
  - `club_detail/`ページの「選手情報」タブ（クラブ別ロースター表示。外国籍選手の同時出場人数制限が
    あるため区分表示を期待したが、番号順の単純なリストのみでセクション分け無し）
  - `roster/`一覧ページの絞り込みセレクタ全種類（`club`/`p`/`c`/`o`/`e`）。国籍系は`c`のみで
    値は空/日本/海外の3つだけ。隠しoption等も無い
  - `club_detail`・`roster`一覧のHTML全文（`外国籍`/`帰化`/`特別枠`/`アジア`等のキーワードで検索）

  そのため以下のハイブリッド方式を採用（`scripts/scrape-roster.ts`の`deriveClassification()`）:
  - 日本人/外国籍: `nationality`（リーグ登録国籍）が「日本」かどうかで自動判定
  - 帰化選手/アジア特別枠: `scripts/lib/playerClassificationOverrides.ts`の手動リスト
    （`playerId → classification`）で個別に上書き。該当2区分は人数が少ない想定のため、
    判明した選手をこのファイルに追記していく運用。ネットワーク取得を伴わないため、リストを
    更新すれば次回`scrape-roster.ts`実行時に全選手へ反映される（新規選手の個人ページ取得とは
    独立して毎回再計算される）
  - **2026-08-13時点でユーザー提供リストを反映済み**: B.LEAGUE全クラブ（B.PREMIER以外含む）の
    帰化枠/アジア特別枠選手リストを、選手名でplayers-master.jsonと突合。B.PREMIER26クラブ中
    15クラブ分がマッチしてoverridesに反映（内訳: 帰化選手6名／アジア特別枠9名。全体では
    日本人148／外国籍46／帰化選手6／アジア特別枠9の計209名）。残り10クラブ（仙台・秋田・
    アルバルク東京・東京SR・富山・信州・三遠・シーホース三河・佐賀・島根）は該当選手名で
    ヒットしなかった（2026-27ロースター未発表または当該選手が一覧に未反映のため）。
    ロースター発表が進み次第、再度name突合すれば拾える見込み
- 2026-27シーズンは調査時点（2026年8月・開幕前）でまだ半数近くのクラブがロースターを
  発表していない（`e=在籍中`で0名になるクラブが複数あった）。これはスクレイパーの不具合ではなく
  実際のサイト側のデータ未整備。シーズン接近とともに再実行すれば自然に埋まっていく
`classification` は `日本人 / 外国籍 / 帰化選手 / アジア特別枠` を想定。

集計（`teams.json` / `players.json`）は生データから**都度計算で再生成可能**にし、生データを正とする。

## 6. 集計ロジック（スタッツ計算式）

### 基本スタッツ
PTS, OREB/DREB/REB, AST, STL, BLK, TOV, PF, FG(M/A/%), 3P(M/A/%), FT(M/A/%), MIN
→ シーズン合計・平均（Per Game）、スタメン/ベンチ別、国籍区分別、シチュエーション別（時期・勝敗・直近N試合）
にフィルタして再集計できる設計にする

### アドバンスドスタッツ（Bリーグ公式定義を優先し、NBA流で補足）

方針: **Bリーグ公式の「スタッツ用語解説」（`https://www.bleague.jp/glossary/`）に定義がある
項目はその式をそのまま採用する**。公式に定義がない項目のみ、NBA/Basketball-Reference流の
一般的な式で補う。これにより、放送や公式サイトで見る数字とズレない値を出せる。

**Bリーグ公式の定義（確認済み・採用）**:
- **POSS（ポゼッション）**:
  `0.5 × ((FGA + 0.4×FTA − 1.07×(OR/(OR+相手DR))×(FGA−FGM) + TO)
        + (被FGA + 0.4×被FTA − 1.07×(被OR/(被OR+DR))×(被FGA−被FGM) + 被TO))`
  → 自チーム・相手チーム双方の推定ポゼッションを平均する精密な式。**これまで実装していた
  簡易式（`FGA - OREB + TOV + 0.44*FTA`）より精緻なので、公式のこの式に置き換える**
  （すでに実装済みのORtg/DRtg/Paceの数値に影響するため、formulas.tsの修正が必要）
- **PACE**: `試合時間 × (POSS + 被POSS) / (2 × (プレイタイム / 5))` → 既存実装と一致（確認済み）
- **EFG%**: `(FGM + 0.5×3PM) / FGA` → 既存実装と一致（確認済み）
- **TS%**: `PTS / (2 × (FGA + 0.44×FTA))` → 既存実装と一致（確認済み）
- **OFFRTG/DEFRTG/NETRTG**: 100ポゼッションあたりの得点／失点／得失点差（＝100×PTS/POSS。
  上記の公式POSSを使う）
- **EFF（貢献度）**: Bリーグ公式が定義する総合指標。**Game Score（NBA流の代替案）の代わりに
  こちらを採用**する。**実装・検証済み**（`formulas.ts`の`eff()`。GeniusAPI生データに含まれる
  公式EFF値と、1試合53人全員で完全一致を確認済み。この検証方法により、個人単位の被ファウル数
  (FD)・被ブロック数(BSR)がPBPから正しく取得できることも同時に確認できた）
  - 2020-21シーズン以降: `(PTS+AS+BS+ST+FD+TR) − (TO+BSR+F) − (2FGA−2FGM) − (3FGA−3FGM) − (FTA−FTM)`
  - 2019-20シーズン以前: `((PTS+TR+AS+ST+BS) − (2FGA−2FGM) − (3FGA−3FGM) − (FTA−FTM) − TO) / 試合数`
  - ⚠️ **年度で式が異なる**ため、Phase 5の過去シーズンバックフィル時にシーズンで式を切り替える
    実装にすること（`aggregate.ts`に分岐は用意済み。現状は2026-27シーズンのみ扱っているため
    新しい式しか使われていない）
- **POSS/PACE/ORtg/DRtg/NetRtg/Usage%/FTR/ORB%: 実装・配線済み**（`aggregate.ts`の出力・
  ランキング/比較/グロッサリーページまで反映済み）
  - **POSS集計の注意点（実装で判明）**: シーズン合計の基本カウント統計に公式POSS式（比率項を
    含む）を再適用すると、非線形性により誤差が出ることが判明。正しい方法は、**GeniusAPI生データの
    各試合のチーム行に既に入っている公式POSS値をそのまま試合ごとに合算する**こと（式を
    再計算しない）。実データで自チーム/相手チーム行が同一値になることも確認済み
  - **Usage%の検証**: GeniusAPI生データの個人行に`USG`フィールドが実在し、実装したNBA流の式と
    完全一致することを確認（EFFのときと同様の検証パターン）
- **+/-（個人単位）**: 「その選手が出場していた時間帯のチーム全体の得失点差」。Bリーグ公式が
  個人スタッツとして定義している。これは**ティアC「ラインナップスタッツ」「オンコート/
  オフコートスタッツ」よりずっと単純**（5人の組み合わせ追跡が不要で、個人の出場区間だけ
  追えばよい）。選手交代のActionCD1コード確認（11章）が前提だが、確認でき次第、ラインナップ
  系より優先して着手する価値がある
- **%-share系（公式定義あり、box scoreのみで算出可・tier A）**: `%PTS`, `%FGM`, `%FGA`,
  `%3PM`, `%3PA`, `%FTM`, `%FTA`, `%OREB`, `%DREB`, `%REB`, `%AST`, `%TOV`, `%STL`, `%BLK`,
  `%BLKA`, `%PF`, `%PFD` — いずれも「個人の数値／チームの数値」のシンプルな比率。**12章の
  「AS%」の扱いを訂正**: Bリーグ公式の`%AST`（個人アシスト数／チームアシスト数）はbox score
  のみで算出できるtier A。一方、ユーザーが元々挙げていたチームレベルの「AS%＝FG成功のうち
  アシストが付いた割合」は別概念で、こちらは引き続きショット単位のアシストフラグが必要（tier B）
- **得点内訳系（公式の略称、12章のプレータイプ内訳と対応）**: `PITP`(Points In Paint),
  `FBPS`(Fastbreak Points), `2NDPTS`(Second Chance Points), `PTSOFFTO`(Points Off
  Turnovers) — いずれも公式に定義された実在の指標であることを確認（`Summaries`に含まれる
  ことは2-2章で確認済み）
- **BSR（被ブロック）**: 公式に個人・ボックススコア両方で定義された指標

**Bリーグ公式に定義がない項目（NBA流で補足・そのまま採用）**:
- **Usage%**: `100 * ((FGA + 0.44*FTA + TOV) * (TeamMIN/5)) / (MIN * (TeamFGA + 0.44*TeamFTA + TeamTOV))`
  → Bリーグ公式に相当する定義なし。NBA流をそのまま採用
- **FTR（フリースローレート）**: `FTA / FGA` → 公式に定義なし、NBA流を採用
- **ORB%（オフェンスリバウンド率）**: `100 * TeamOREB / (TeamOREB + OppDREB)` → 公式のPOSS式
  内に同じ考え方の項があるが、独立した指標としては定義されていない。NBA流を採用
- PERはリーグ全体係数が必要で複雑なため引き続き後回し候補

**未確認・公式に見当たらなかった項目**: デッドTOV／ライブTOV（ターンオーバーの種別分け）は
Bリーグ公式の用語解説には存在しない。ユーザー独自の集計軸と思われるため、12章の通りtier B
（ActionCD1のイベント種別分類に依存）のまま進める。

### Netスタッツ・勝敗傾向
- Net = 自チームスタッツ − 相手チームスタッツ（試合別／シーズン平均）
- 勝敗傾向: ホーム/アウェイ別、連勝連敗、対戦順位帯別の成績

### 順位表関連
- 順位遷移・勝ち星推移・貯金（勝−敗）推移: シーズン内の全試合を日付順に走査し、各日付時点の
  累積成績から順位表を再現（`standings-history.json` に日付ごとスナップショットを保存）
- **同率タイブレーク（実装済み）**: 勝率降順 → 得失点差降順のシンプルな方式を暫定採用。
  `aggregate.ts` の `buildStandingsHistory` 内1箇所に集約してあるため、公式の正式ルール
  （直接対決成績等）が判明次第、その1箇所を差し替えれば全体（全体順位・地区内順位とも）に反映される
- **東西地区制（実装済み）**: B.PREMIERは2026-27シーズンから26クラブが東西2地区（各13クラブ）に
  分かれる。GeniusAPIのレスポンスには地区情報が含まれないため、`scripts/lib/divisions.ts`に
  TeamID→地区のマスタをハードコードして対応（`bleague.jp/standings/`で実際の割り当てを確認済み）。
  ⚠️ **地区分けはシーズンごとに固定ではない**（2025-26→2026-27でFE名古屋・越谷アルファーズが
  外れ、信州・神戸が新規参入するなど変動あり）。また**2025-26シーズン以前はB1/B2/B3の
  昇降格制であり、そもそも東西地区という概念自体が存在しない**。そのためPhase 5の過去
  シーズンバックフィル時は、地区マスタに無いチームは`division`が`undefined`になる設計
  （実装済み・動作確認済み）で自然に無効化される。現在のマスタは「2026-27シーズン基準」限定
  であることを明示しておくこと
- StandingsPageの「現在の順位表」は東地区・西地区の2テーブルに分割表示。順位遷移等の推移
  グラフは全チームまとめたまま（地区別に分けていない）
- **星取り表（実装済み）**: 全チーム×全チームのマトリックス（対戦成績・合計得失点差）＋
  対東地区/対西地区の成績サマリー。StandingsPageに追加。配色・26チーム分のレイアウト調整は
  実シーズン開幕後に見て判断する方針で保留中
- マジックナンバー・プレーオフ進出条件（各地区上位3クラブ＋ワイルドカード上位2クラブ、計8クラブ）:
  スコープ外、シーズンが進んでから対応

### ティアC（ラインナップ／オンオフコート）
- `playByPlay` の `substitution` イベントを時系列に走査し、各時点の5人（両チーム計10人）を
  シミュレーションで復元
- 各選手が「コート上にいた区間」のチーム得失点を積算 → オンコート/オフコートのNetスタッツ
- 5人の組み合わせ単位でも同様に区間ごとの得失点を積算 → ラインナップスタッツ
- 精度検証: 各選手の「コート上区間合計」がボックススコアの `MIN` と一致するかをチェックし、
  乖離が大きい試合はデータ欠損として除外またはフラグ付けする

## 7. 画面構成（フロントエンド）

1. **試合詳細ページ**: スコアボード（Q別得点）／ボックススコア（スタメン・ベンチ別）／
   ゲームリーダー／キースタッツビジュアライザ／Lead Tracker（タイムアウトプロット付）／

3. **チーム詳細ページ**: シーズン成績、個人スタッツ、勝敗傾向、スタッツリーダー、

4. **個人スタッツ一覧**: シーズン選択、チーム/選手フィルタ、ソート、国籍区分フィルタ
5. **個人詳細ページ**: シーズン成績、試合ごとのログ、通算成績、オンコート/オフコートスタッツ
6. **比較ページ**（チーム／個人共通）: 複数チーム・選手を選んで並べて比較
7. **ランキングページ**: 各スタッツのリーグ全体ランキング、画像出力。**国籍フィルタ実装済み**
   （個人モード時に「すべて/日本人選手/外国籍選手」の2値で、`nationality`ベースの簡易フィルタ。

## 8. 自動更新フロー（GitHub Actions）

### 8-1. 新規試合の取得と、既存試合の再チェック（スタッツ修正対応）

公式記録は試合後に修正が入ることがあり、経験上**試合終了から約1週間後に数値が修正される
ケースがある**。そのため毎回の実行で「新規試合の取得」だけでなく「直近試合の再取得・差分検知」
を必ず行う。

- **対象範囲**: `meta.status` が `"watching"` の試合（＝直近の一定期間内の試合）は毎回再取得する
- **監視期間**: 試合終了から**14日間**を再チェック対象とする（「約1週間で修正される」に対し、
  検知漏れを防ぐため約2倍のバッファを確保。日数は運用しながら調整可能なパラメータにする）
- **監視終了**: 監視期間を過ぎたら `status` を `"final"` にして再チェック対象から外す
  （スクレイピング量を抑えるため。ごく稀に14日超で修正が入った場合は手動で個別再取得できる
  コマンドも用意しておく）
- **差分検知**: 新しく取得したボックススコアと保存済みJSONを比較し、値が変わっていれば
  - 該当 `games/{scheduleKey}.json` を上書き、`meta.lastChangedAt` と `revisionCount` を更新
  - その試合が属するシーズンの `teams.json` / `players.json` / `standings-history.json` を
    **必ず全量再計算する**（生データが正、集計は都度生成し直す設計のため、部分的な差分反映は
    せず毎回作り直すことで修正の反映漏れを防ぐ）
  - 変更内容は簡易ログ（例: `data/changelog/{season}.log`）に追記し、後から「いつ何が修正されたか」
    を追えるようにしておく（任意だが推奨）

### 8-2. スケジュール収集の頻度（フル収集 vs 日次の軽量チェック）

実装検証の結果、シーズン全体のスケジュール一覧を1回フル収集すると約500リクエスト・
2.5秒間隔で約20分かかることが判明した。これを毎日のcronにそのまま含めると実行時間・
サーバー負荷の両面で無駄が大きいため、以下のように分離する。

- **フル収集**（`scrape-schedule.ts` の全件モード）: シーズン開幕時、または延期・日程変更が
  疑われるタイミングでのみ、手動（`workflow_dispatch`）または週1回程度の別ジョブとして実行
- **日次cron**: 直近数週間分（前後2週間程度）のスケジュール・試合結果のみを軽く再チェック。
  対象範囲は8-1章の「14日間watching」の仕組みとほぼ同じなので、同じジョブ内で統合してよい

### 8-3. データサイズへの対応（実装済み・2026年8月13日）

1試合分の生データ（PlayByPlaysの座標込み）は約700KBあり、フルシーズン500試合超で350MB前後に
なる見込み。**Phase 5の過去シーズン一括バックフィル前に方針を決めて実装した**（後から大量データを
圧縮し直すのは無駄なため）。

**実装方針**: 全JSONを `.json.gz` として保存する。`scripts/lib/storage.ts`の`writeJson`/
`readJson`/`writeGameFile`/`readGameFile`/`readAllGames`に圧縮・伸長を透過的に組み込み、
呼び出し側（`aggregate.ts`・`scrape-boxscore.ts`等）は従来通り拡張子`.json`のパスを渡すだけで
よい（実体ファイル名への`.gz`付与・削除は`storage.ts`内に閉じている）。フロントエンドは
`src/lib/data.ts`の`fetchJson`で`.gz`付きURLを取得し、`DecompressionStream` APIでその場展開する。

**実データでの圧縮率**: 既存data/配下（191ファイル・5.24MB）を`scripts/migrate-gzip.mjs`で
一括変換した結果、0.32MBまで圧縮（**93.8%削減**）。想定通りの圧縮率だった。

⚠️ **実装時に発見した環境差異**: Vite開発サーバー（dev server）は`.json.gz`ファイルを
`Content-Encoding: gzip`ヘッダ付きで返し、ブラウザの`fetch`自体が透過的に展開してしまう
（この場合`res.body`は既に展開済みの生JSONで、追加で`DecompressionStream`にかけると
`TypeError: Failed to fetch`になる）。一方GitHub Pages等の素の静的ホスティングはそのような
透過展開をしないため、レスポンスは圧縮バイト列のまま届く想定。`fetchJson`はレスポンスの
`Content-Encoding`ヘッダの有無を見て、既に展開済みならそのまま`res.text()`、そうでなければ
`DecompressionStream`で展開する、という両対応の実装にした（本番ビルド`dist/`には実際に
gzip圧縮されたファイルが出力されることを`file`コマンドで確認済み）。

### 8-4. GitHub Actions ワークフロー（イメージ）

```yaml
on:
  schedule:
    - cron: "0 18 * * *"   # 毎日JST3時（UTC18時）。試合日程に合わせ調整
  workflow_dispatch: {}
jobs:
  update:
    steps:
      - checkout
      - 直近数週間分のスケジュール再チェック（8-2参照。フル収集は含めない）
      - 新規試合のスクレイピング（未取得試合分のボックススコア・PBPを取得）
      - 直近14日以内の"watching"試合を再取得し、差分があれば上書き（8-1参照）
      - 監視期間を過ぎた試合を"final"に更新
      - 集計再計算（games/*.json全体からteams/players/standings-historyを再生成）
      - 差分があればcommit & push
```
- シーズンオフはcron停止 or 差分なしで実質何もしない
- 過去シーズンのバックフィルは通常運用のcronとは別の一回限りのスクリプトとして、
  サーバー負荷をかけすぎないようゆっくり実行する（バックフィル時点で試合終了から
  14日以上経過している試合は最初から`status: "final"`として取り込んでよい。8-3章の
  圧縮方針もこのタイミングで適用する）

  - `4`/`6`: サイドのペイント外2P（θ約±35〜79度のミラーペア）
  - `5`: ミッドレンジ中央（r 4.5〜6.3m、θ約±28度以内）
  - `8`/`12`: コーナー3（r 6.8〜7.2m、θ約±81〜94度のミラーペア）
  - `9`/`11`: ウイング3（r 7.0〜8.4m、θ約±23〜72度のミラーペア）
  - `10`: トップ・オブ・ザ・キー3（r 7.1〜8.7m、θ約±19度以内）
  - `13`: ヒーブ（r>11m、稀・低確率）

  従来の実装（初回リリース時）はSide（"left"/"right"、どちらのバスケットへのショットか）に応じて
  X軸のみ反転していたが、**Yも反転しないと座標が正しく揃わない**ことが今回のAreaCD調査で判明した。
  同一チーム・同一シーズンでも、Side="left"時とSide="right"時とで同じAreaCD値のショットの絶対Y座標が
  正反対になる（例: AreaCD=9はSide=left時に平均Y=82.9、Side=right時に平均Y=18.3）。これは
  AreaCDがアタッキングチーム視点の左右で採番されていることを意味し、コート幅方向の絶対位置(Y)は
  Sideに紐づかない一貫した値ではなかった。X・Y両方を反転する（180度回転）ことで、同一選手・
  同一チームのショット傾向が試合を通して同じ側に一貫して表示されるよう修正済み（`src/lib/shotChart.ts`）。
  
  ゾーン別ヒートマップ表示（試合詳細ページのショットチャート「エリア別成功率」ビュー）は、
  AreaCD値そのものではなく上記r・θの境界値を使って幾何学的に分類する方式で実装した（AreaCD値には
  外れ値が混じることがあり、距離・角度ベースの分類の方が堅牢なため）

**実装への反映**:
- ティアAの項目（基本得点・シュート基本・リバウンド/AST・TOV合計・STL/BLK・ファウル・
  二桁得点人数・eFG%/FTR/ORB%/TS%・レーティング・それらのNet版）は **Phase 1〜2** で対応
- ティアBのうち「プレータイプ内訳」「ターンオーバー内訳」は、**Phase 3で「ゲームスコア/試合成績」
  APIを調査した結果**、公式に取得できるなら実装は比較的容易（tier Aに格上げ可能）。
  取得できない場合はPBP（テキスト速報）からの推定になり、精度検証が必要（12章の投資判断ポイント）
- ショットチャート依存の項目（ペイント内外、Mid Range、被ブロック）は**2022-23シーズン以降のみ**
  対応可能という前提を、過去シーズンのバックフィル（Phase 5）時に明示する

**個人+/-実装メモ（2026年8月13日）**: 当初はPlayByPlaysのActionCD1=86/87（選手交代イン/アウト）
から在コート選手を復元し、得点イベントのたびに加減算する自前再構築を想定していたが、着手前に
`HomeBoxscores`/`AwayBoxscores`の個人行を確認したところ、公式の`PLUSMINUS`フィールドが既に
存在し、かつ値も妥当（DNP選手は0、出場選手は試合展開と整合する符号・大きさ）であることを確認した。
POSS/EFF/USGのときと同じ「まず生データに公式フィールドが無いか確認してからロジックを自作する」
という方針が功を奏し、PBP再構築・在コート人数検証・MIN一致検証は不要になった。この経緯は
今後似た指標（例: ラインナップスタッツ）を検討する際も、まず生データの全フィールドを確認してから
着手する、という教訓として残す。
