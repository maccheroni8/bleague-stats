# Bリーグ個人用スタッツサイト 設計書 (v2)

> このドキュメントは Claude Code に実装を依頼するための引き継ぎ資料です。
> 上から順に「何を」「なぜ」「どう作るか」を記載しています。実装時に不明点があれば

## 1. プロダクト概要

- **目的**: B.LEAGUE（https://www.bleague.jp/）の個人専用スタッツサイトを作る
- **優先カテゴリ**: B.PREMIER（最優先。B.ONE / B.NEXTは当面対象外）
- **対象シーズン**:
  - 最優先: 2026-27シーズン（2026年10月開幕）を全試合カバー
  - 過去データ: 理想は2016-17シーズン（B.LEAGUE発足）以降の全シーズン。
    実装難易度が高い場合は「直近3シーズン」まで縮小可、それも厳しければ
    「新シーズンのみ」でリリースし、過去データは後日バックフィルする
  - 注意: ショットチャート等一部の可視化データは公式サイト上でも2022-23シーズン以降にしか
    存在しない可能性が高い。過去シーズンは機能によって対応範囲が変わることを許容する
- **提供形式**: チームスタッツ／個人スタッツ／試合詳細／順位表　それぞれ一覧＋詳細
- **利用者**: 開発者本人のみ（外部公開は前提としない。閲覧認証は不要）
- **関連プロジェクト**: 既存のブレックス観戦カレンダーPWA（Firebase + GitHub Pages）
  とは**別リポジトリ・別プロジェクト**として新規に作成する（技術スタックの知見は流用可）

## 2. データソースと制約

B.LEAGUE公式サイトに一般公開APIは無いため、公式サイトのHTML／内部データをスクレイピングして
取得する。`game_detail` ページの調査により、公式サイトには以下のセクションが既に存在することを
確認済み（＝該当データは公式に公開されている）。

| 用途 | URL例 / セクション | 備考 |
|---|---|---|
| 試合スケジュール一覧 | `https://www.bleague.jp/schedule/?data_format=json&year=...&mon=...&day=...&event=...` | HTMLではなくAJAX用のJSON APIが存在することを確認済み（2-2章）。ScheduleKey一覧をHTMLパース不要で取得可能 |
| ボックススコア | `https://www.bleague.jp/game_detail/?ScheduleKey=XXXXXX&tab=2` | 選手別・チーム別の基本スタッツ。Q別得点・スタメン表記も含まれる想定 |
| ゲームリーダー | 同ページ内セクション「ゲームリーダー」 | チーム別スタッツ上位者。box scoreから自前集計でも代替可 |
| スコアチャート | 同ページ内セクション「スコアチャート」 | JS描画。裏にAPI/JSONがある可能性が高く、**実装着手時に最優先で調査**（Lead Tracker実現の鍵） |
| ゲームスコア／試合成績 | 同ページ内セクション「ゲームスコア」「試合成績」 | JS描画（今回のfetchでは値が"--"表示で内容未確認）。Fastbreak Points・Points In Paint・Bench Points・eFG%等、詳細なチーム比較スタッツが含まれている可能性が高い。**スコアチャートと同様に最優先で裏側データを調査**（12章のチームスタッツ項目カタログの多くがここに依存） |
| ショットチャート | 同ページ内セクション「ショットチャート」 | 2022-23シーズン以降のみ存在（それ以前は無い想定） |
| テキスト速報 | タブ「テキスト速報」 | 得点・タイムアウト・選手交代等の時系列イベントログの可能性。Lead Tracker/交代バー/ラインナップスタッツの代替データ源 |
| 選手・チーム個別ページ | `https://www.bleague.jp/roster/` 配下の選手詳細ページ | 国籍・登録区分（日本人/外国籍/帰化/アジア特別枠）、身長・体重・生年月日等のプロフィール情報 |
| 成績詳細（検証用） | `https://www.bleague.jp/stats/` | 自作集計値の突合・検証に使える |
| 順位表（シーズン一覧の確認） | `https://www.bleague.jp/standings/` | シーズンプルダウンが 2016-17〜2026-27 まで存在することを確認済み |

### 2-1. 試合詳細データの裏側API（検証済み・Phase 1はこの方式で進行）

`game_detail` ページが読み込む `genius_game_new2208.js` のソースに、ボックススコア・
プレイバイプレイ・Q別得点等を配信するJSON APIのURLパターンが書かれていることを発見し、
**Claude Codeによる実機検証で実際に取得できることを確認済み**。HTMLスクレイピングではなく
**このJSON APIを直接叩く方式でPhase 1を進める**（詳細は2-2章の検証結果を参照）。

**確認できたURLパターン**（`_contexts.scheduleKey` は対象試合の `ScheduleKey`）:
```
1. http://b-league.s3.amazonaws.com/web_json/v2_genius_contexts/{ScheduleKey}/latestid
   → その試合の最新リビジョンID（整数）を返す
2. http://b-league.s3.amazonaws.com/web_json/v2_genius_contexts/{ScheduleKey}/{latestid}.json
   → 試合の全データ（Game / PlayByPlays / HomeBoxscores / AwayBoxscores / Summaries）
```
コード中には `dev-bleague.s3.amazonaws.com`（検証用）という変種も存在したが、**Claude Codeの実機
検証により、どちらか一方が実際に有効であることを確認済み**（詳細は2-2章）。
なお、B3の試合は `v1_contexts` という別パスを使っている形跡があり（B.PREMIER優先の本プロジェクトでは
直接関係しないが留意）、ショットチャートと同様にこの仕組みは**2022-23シーズン以降のみ**対応している
可能性が高い（box scoreのヘッダー描画ロジックが `game_year >= 2022` で分岐している）。過去シーズンの
バックフィル時に別途確認が必要。

**確認できたJSONのフィールド名（ソースコードの参照箇所から）**:
- `Game`: `GameDateTime`, `GameCurrentPeriod`, `MaxPeriod`, `HomeTeamScore`, `AwayTeamScore`,
  `HomeTeamScore01`〜`14`/`AwayTeamScore01`〜`14`（Q別・OT別得点）, `GameEndedFlg`, `RecordFixedFlg`
  （← **8章で設計した「試合確定/修正監視」のstatus判定にそのまま使える**）, `ConventionKey`,
  `ConventionNameJ`, `Attendance`, `RefereeNameJ`, `SubRefereeNameJ1/2`, `HomeTeamID`, `AwayTeamID`,
  `PlayByPlayExistsFlg`, `BoxscoreExistsFlg`
- `PlayByPlays[]`: `Period`, `ActionCD1`（イベント種別コード）, `RestTime`（残り時間）, `PeriodEndRowFlg`
- `HomeBoxscores[]` / `AwayBoxscores[]`: `PeriodCategory`（1〜4=各Q、18=試合全体。**Qごとのボックス
  スコアがそのまま取れる**）, `PT2M`/`PT2A`, `PT3M`/`PT3A`, `FTM`/`FTA`, `FG%`/`2FG%`/`3FG%`/`FT%`,
  `TR`, `Category`（選手行かチーム合計行かの区別）
- `Summaries`: シーズン平均の比較データ（ヘッダーのPPG/FG%等の元）

**`ActionCD1`（プレイバイプレイのイベント種別コード）の対応表（アイコン割り当てから逆算）**:
| コード | 意味 |
|---|---|
| 1 | 3P成功 |
| 3, 4 | 2P成功 |
| 7 | フリースロー成功 |
| 15, 20〜26, 46 | ファウル |
| 86, 87, 89 | 選手交代（イン/アウト） |
| 88, 90 | タイムアウト |

**選手交代・タイムアウトのコードは確定済み**（2026年8月13日、`genius_game_new2208.js`の
ソースコードを直接特定・実データで裏付け。詳細は2-2章末尾）。

**この発見のインパクト**: `PlayByPlays` に**タイムアウトと選手交代がイベントコードとして明確に
記録されている**ことが分かったため、12章までは「テキスト速報の自由記述をパースする」前提だった
Lead Tracker・タイムアウトプロット・選手交代バー・ラインナップ/オンコートオフコートスタッツが、
**同一の構造化JSONから直接構築できる可能性が高い**（テキストの曖昧なパースが不要になる）。
これにより3章・12章のティア判定を以下のように更新する：
- Lead Tracker／リード時間／タイムアウトプロット：ティアB→**ほぼティアA相当**（要フィールド確認だが
  スコアチャートと同じデータ源であることが確認済み）
- 選手の出場交代バー／ラインナップスタッツ／オンコート・オフコートスタッツ：ティアCのままだが、
  「テキスト解析による精度リスク」から「構造化イベントデータのパース精度検証」に性質が変わり、
  リスクは大きく下がった（選手ID/チームIDが各イベントにどう紐付くかは要確認）

### 2-2. 検証結果（確定・6試合4,513件のPlayByPlaysで検証済み）

Claude Codeによる複数試合サンプルでの実機検証が完了。以下は確定情報として扱ってよい。

**OT（延長戦）の扱い**:
- `HomeTeamScore05`/`AwayTeamScore05` はOT発生時のみ動的に追加される（通常試合には存在しない）
- `MaxPeriod` は延長でも `4` のまま変わらない（レギュレーションQ数の固定値）。延長判定には
  `GameCurrentPeriod=5` かScoreフィールドの存在数を見る必要がある
- `PeriodCategory` はOT試合で `5`（OT本体）・`17`（延長合計）が追加される。1OTのみの試合では
  この2つの値が完全一致することを確認済み。**複数OT時の挙動は未検証**（プレーオフ等でOTが
  2回以上続いた試合があれば追加確認が望ましい。低頻度の事象なので実装のブロッカーではない）

**`Category` の意味（5試合で比較し確定）**:
- `Category=1` ＝ 個人選手行
- `Category=2` ＝ 個人に紐付かないチーム発生イベント行（チームリバウンド／チームターンオーバー
  のみ非ゼロ）
- `Category=3` ＝ 真のチーム合計行（`PlayTime`が200:00＝40分×5人、`Point`が最終スコアと一致）
  → **チームスタッツの集計はこの行を正として使うのが最も簡単で確実**

⚠️ **`PeriodCategory`が18（試合全体）以外の行は、多くの数値フィールドが空文字`""`になる
（2026-08-17、ボックススコア全面改修の実装中に発見。1試合・504739で確認、他試合も同傾向と
推測される）**。`shared/types.ts`の`BoxscoreRow`は該当フィールドを`number`型と定義しているが、
実データはこの型定義通りになっていない。影響度はCategory・PeriodCategoryの組み合わせで異なる:
- `Category=1`（個人）: Q別（1〜4）・試合全体（18）は全フィールド数値。**前半/後半集計行
  （15/16）のみ**`PLUSMINUS`/`AST_TO`/`EFG`/`TS`/`USG`が空文字になる
- `Category=2`（TEAM/COACHES）: Q別（1〜4）は`FOUL`/`RB_OFF`/`RB_DEF`/`RB_TOT`/`TO`/`OFFRTG`/
  `DEFRTG`以外のほぼ全フィールドが空文字。前半/後半（15/16）もPOSS系・レーティング系・
  `PLUSMINUS`等が空文字。試合全体（18）は数値フィールドの空文字化なし
- `Category=3`（チーム合計）: Q別（1〜4）は数値フィールドの空文字化なし。前半/後半（15/16）は
  `POSS`/`OFFRTG`/`DEFRTG`/`NETRTG`/`EFG`/`TS`/`AST_TO`が空文字。試合全体（18）は空文字化なし

これまでの実装（`aggregate.ts`・`onCourt.ts`・`situational.ts`・試合詳細ページのQ別得点表/
Lead Tracker/出場交代等）は**すべて`PeriodCategory=18`の行のみを読むか、`PlayByPlays`を独自に
集計しており、この空文字フィールドには触れていなかったため影響なし**（2026-08-17に横断確認済み）。
初めてこの問題が顕在化したのは、ボックススコアのQ別/前後半トグル機能で`Category=1/2/3`の
Q別・前後半行を横断して数値を合算した時（`src/lib/boxscoreAggregate.ts`の`sumCounts`）。
**今後、`PeriodCategory=18`以外の行の数値フィールドを新たに読む実装をする場合は、必ず
`typeof value === "number"`で空文字を弾いてから使うこと**（`sumCounts`内の`num()`ヘルパーと
同じパターン）。

**`ActionCD1` の全体像（6試合・4,513件を走査し32種類を確定）**:
3P/2Pの成功・失敗の細分化、パーソナル/オフェンス/アンスポーツマンファウルの区別など、当初の
推測表よりかなり詳細なことが判明。`20, 21, 24, 26, 46, 89, 90`（テクニカルファウル等と推測）は
今回未出現。**運用方針**: 未知のコードが来たらエラーにせずログに記録して集計は継続する
（8章の差分検知の仕組みと同様、「知らないデータに遭遇したら気づけるようにする」設計にする）。

✅ **`20`・`21`・`24`は確定済み（2026年8月16日、試合詳細ページのTEAM/COACHES欄調査の一環で
複数シーズンのPlayByPlaysを走査し`PlayText`で裏付け）**:
- `20` ＝ コーチテクニカルファウル（`PlayText`「テクニカルコーチファウル」。`PlayerID1`はnull）
- `21` ＝ ベンチテクニカルファウル（`PlayText`「テクニカルベンチファウル」。`PlayerID1`はnull）
- `24` ＝ 選手個人のテクニカルファウル（`PlayText`「#0 フランクス テクニカルファウル」のように
  実在の選手に紐付き、`PlayerID1`が入る）

`20`・`21`はチームに帰属し選手に紐付かないため、発生した`Period`の`Category=2`行（チーム発生
イベント行）の`FOUL`が加算されることを実データで確認した（ScheduleKey 504733、アルティーリ千葉、
Period 3の例）。これは「`Category=2`はチームリバウンド／チームターンオーバーのみ非ゼロ」という
上記の記載を更新する新事実（コーチ/ベンチのテクニカルファウルもここに乗る）。また、
`genius_game_new2208.js`のソースコード上、`Category==2`の行は表示名が明示的に
`bs.BSDisplayName = 'TEAM / COACHES'`とハードコードされていることも確認済み（bleague.jpの
ボックススコアが「TEAM/COACHES」と表示している実体はこの行そのもの）。
残る未確認コードは`26, 46, 89, 90`（`89`・`90`は2-4章で選手交代スワップ・タイムアウトの
コードと確定済みのため、こちらは「テクニカルファウル等」ではない別の意味の可能性が高い）。

✅ **解決済み（2026年8月13日）**: 未出現だった `89`・`90` を含む選手交代・タイムアウトの
`ActionCD1`コードは、観測に頼らず`genius_game_new2208.js`のソースコード（`EventIcons`
オブジェクトのアイコン割り当てロジック）を直接読むことで確定した。加えて4試合・3,043イベントの
実データで`PlayText`（`"プレイヤーイン"` `"プレイヤーアウト"` `"タイムアウト"`）による裏付けも
取れている。詳細・確定表は2-2章末尾を参照。Lead Tracker・選手交代バー・ラインナップスタッツ
（ティアB/C）着手のブロッカーは解消。

**副産物の発見（想定より楽観的な方向に更新）**:
- `Summaries` に **Fastbreak Points / Points In Paint / Second Chance Points が直接含まれている**
  → 12章「プレータイプ内訳」はテキスト速報頼みの想定が外れ、**ティアA相当に格上げ**
- PlayByPlaysのシュートイベントに **`X`/`Y`/`AreaCD`（座標）が同梱** → ショットチャートも
  同一APIで完結する見込み（ただし2022-23シーズン以降のみという season制約は別途残る）

検証用スクリプトは `scripts/` 配下に保存済み。上記を踏まえ、**Phase 1のスクレイパー本実装
（`scrape-boxscore.ts` 等）に進んでよい**。

### 2-4. 選手交代・タイムアウトのActionCD1コード確定（2026年8月13日）

11章で積み残していた「選手交代・タイムアウトのActionCD1コードが未観測」という課題を解決。
観測に頼る方式（多くの試合を集めてコード出現頻度から逆引きする）ではなく、`game_detail`ページが
読み込む`genius_game_new2208.js`（実際のURL: `https://bleague.bl.kuroco-img.app/v={hash}/files/js/front/user/genius_game_new2208.js`。
`{hash}`はキャッシュバスティング用のバージョン番号でデプロイのたびに変わる。`game_detail`ページの
`<script src>`から都度取得するのが確実）のソースコードを直接読み、アイコン割り当てロジック
`EventIcons`オブジェクトからコードを特定した：

```js
var EventIcons = {
    "1": 3, "3": 2, "4": 2, "7": 1,
    "15": ".../icon-f.svg", "20": ".../icon-f.svg", ..., "46": ".../icon-f.svg",
    "86": ".../icon-inout.svg",
    "87": ".../icon-inout.svg",
    "88": ".../icon-t.svg",
    "89": ".../icon-inout.svg",
    "90": ".../icon-t.svg"
};
```

**確定した対応（以前の推測表と完全一致）**:
| コード | 意味 | 実データでの裏付け |
|---|---|---|
| 86 | 選手交代・イン | `PlayText: "#5 テリー プレイヤーイン"`（4試合中70/88/71/76回観測） |
| 87 | 選手交代・アウト | `PlayText: "#13 津山 プレイヤーアウト"`（4試合中60/78/61/66回観測） |
| 89 | 選手交代関連（未観測） | ソース上は86/87と同一`icon-inout.svg`を割当。4試合には未出現だが、割当ロジック自体は確定 |
| 88 | タイムアウト | `PlayText: "タイムアウト"`。`HomeAway`が数値＝通常のチームタイムアウト、
  `HomeAway === null`のときはソース側で「オフィシャルタイムアウト」表記に切り替わる（4試合中9〜11回観測） |
| 90 | タイムアウト関連（未観測） | ソース上は88と同一`icon-t.svg`を割当。ただしソース内に
  `ActionCD1 == 90`のときだけ`PlayText`に「タイムアウト」を追記する専用分岐があり、
  88とは何らかの形で区別されている（オフィシャルタイムアウトとは別の値であるため、
  ビデオチャレンジ関連等の可能性はあるが未確認。低頻度事象と推測され、実装のブロッカーではない） |

**選手交代イベントの構造**: 1イベント＝1選手（`PlayerID1`/`PlayerNameJ1`/`PlayerNo1`）で、
IN・OUTはそれぞれ独立した行として記録される（1つのイベントにIN/OUT両方の選手情報が同梱される
構造ではない）。ラインナップ復元時は、同時刻・同チームのIN行とOUT行をペアリングする実装が必要。

**検証方法**: `data/2025-26/games/*.json`（4試合・PlayByPlays計3,043件）を集計し、86・87・88の
出現回数が試合として妥当な範囲（1試合あたり交代60〜100件強、タイムアウト9〜11件）であることを
確認。89・90は今回のサンプルには出現しなかったが、観測頼みではなくソースの割当ロジック自体を
直接確認したため、確定情報として扱ってよい。

### 2-5. Lead Tracker実装（2026年8月13日）

得失点差の推移をグラフ化する「Lead Tracker」を実装。データソースは新規のバックエンド集計を
追加せず、既に`games/{scheduleKey}.json`に保存済みのPlayByPlaysをフロントエンドでその場整形する
方式を採用（`src/lib/leadTracker.ts`）。

**時間軸の作り方**: PlayByPlaysの`RestTime`（そのピリオドの残り時間）を「試合開始からの累計経過秒」
に変換する。ピリオドの秒数はB.LEAGUE公式ルール通り各Q10分・延長(OT)5分固定とし、実データ
（延長開始行の`RestTime`が"5:00"であること）でも裏付け済み。公式サイトのスコアチャート実装
（`PBPGraphBuilder`）は各ピリオドを固定幅の列に押し込めて表示する方式（延長も見た目上は他Qと
同じ幅になるよう時間を2倍スケールする専用ロジックがある）だが、本実装は「Q跨ぎを含めた連続した
経過時間」を軸にしたかったため、この実際の経過秒をそのままX軸に使う独自方式にした（結果として
延長Qは他のQより視覚的に幅が狭く表示され、実際の試合時間の長さの違いが直感的にわかる）。

**得点イベントの特定**: 得点が入るActionCD1コード（1, 3, 4, 7, 44）は、公式サイトのスコアチャート
実装（`PBPGraphBuilder.update`内の`pointsHashTable`）と同じ値を採用。各イベントの`Score`フィールドに
その時点の両チーム累計スコアがそのまま入っているため、得点計算をこちら側で再現する必要はなく、
そのままstep chart（`recharts`の`type="stepAfter"`）のデータ点として使える。

**タイムアウトのマーキング**: 2-4章で確定したActionCD1=88のイベントを、対応する経過秒の位置に
縦の点線（`ReferenceLine`）で表示。`HomeAway`でホーム/アウェイ/オフィシャルタイムアウトを色分け。

**Y軸（得失点差）**: ホームチーム視点の得失点差（ホーム−アウェイ）を、0を必ず跨ぐよう
`[-halfRange, halfRange]`の対称なドメインで表示。0より上をホームチームカラー、0より下をアウェイ
チームカラーで塗り分ける（`linearGradient`のオフセットをドメイン中央=50%に固定することで実現。
対称ドメインなので常に50%になる）。

**画像出力ボタンは非搭載**: 6章で確認済みの制約（html2canvasがrechartsのSVGグラフを正しく
描画できない）に該当するため、他のスタッツランキング等と異なり画像出力ボタンは付けていない。

**動作確認**: 延長なし（ScheduleKey 506099）・延長あり（ScheduleKey 505288）の両方で実データ描画・
ツールチップ表示・コンソールエラー無しを確認済み。505288はOT区間が他のQより狭い幅で正しく
表示されることも確認した。

### 2-6. 在コート状態の復元・精度検証（Phase 4基盤、2026年8月13日）

ラインナップスタッツ／オンコート・オフコートスタッツ（ティアC）の前提となる「PlayByPlaysから
各時点の在コート5人を復元する」ロジックを`shared/onCourt.ts`に実装し、`scripts/validate-oncourt.ts`
（`npm run validate:oncourt`）で精度検証した。**UIには一切組み込んでいない**（検証専用）。

**復元ロジックの要点**:
- 在コートの初期状態はBoxscoreRowの`StartingFlg`では初期化しない。実データを見ると試合開始時点
  （Period1・RestTime10:00）にスタメン5人×2チーム分のActionCD1=86（IN）イベントが明示的に
  記録されていることを確認したため、PBP自体から復元する（BoxscoreRowの`StartingFlg`は
  復元後の突合検証にのみ使う。詳細は下記「判明した問題」参照）
- 得点イベント（ActionCD1: 1, 3, 4, 7, 44。Lead Trackerと同じ公式`pointsHashTable`）のたびに、
  その時点で在コートの選手全員に得失点を加減算し、個人+/-を再計算する
- 選手交代イベント（86=IN, 87=OUT）を同一秒・同一チームでバッチ処理し、バッチ適用後に
  在コート人数が5人になっているかを確認する

**検証結果（4試合・PlayByPlays計3,043件、うちOT2試合）**:
| 検証項目 | 結果 |
|---|---|
| 在コート人数（常に5人か） | 崩れ0件 |
| 選手ごとの在コート時間 vs 公式MIN（±6秒許容） | 85/85人（出場選手全員） = 100% |
| 復元+/- vs 公式PLUSMINUSフィールドの完全一致 | 96/96人（DNP含む全選手） = 100% |

**開発中に発見した2つの問題と対応**:
1. **PlayByPlays配列は必ずしも試合内の時系列順ではない**: ある試合（ScheduleKey 505118）で、
   配列の途中（本来は延長(Period5)の区間）に、通常であればもっと前にあるはずのPeriod1の
   一連のイベントが丸ごと挿入されているのを発見した（恐らく後日の記録修正が反映されたタイミングで
   配列に追記されたことによるものと推測。8章で触れている「試合終了後の記録修正」がPBPレベルでも
   起きている証拠）。対策として、`RestTime`から試合開始からの累計経過秒(elapsedSec)を算出し、
   **配列の並び順ではなくelapsedSecの昇順で全イベントをソートしてから**処理する設計にした
2. **同一秒内のイベント順序を独自ルールで決め打ちすると個人+/-がズレる**: `RestTime`の解像度は
   1秒しかないため、「交代→フリースロー→交代」のように同じ1秒間に複数のイベントが起きるケースが
   ある（シュートファウルの反則直後に交代し、その後フリースローを打つ、等）。当初は「同一秒内は
   得点イベントを交代イベントより先に処理する」という決め打ちルールにしていたが、これだと
   フリースロー**前**に行われた交代（新しく入った選手がフリースローの結果を受け取るべきケース）を
   誤って逆順に処理してしまい、公式PLUSMINUSとズレる原因になっていた。実データを調査した結果、
   **同一秒内では配列に記録された元の並び順が実際の発生順と一致している**ことを確認できたため
   （JavaScriptの`Array.sort`は安定ソートである性質を利用し、elapsedSecが同値の場合は
   独自の優先順位を付けず元の配列順序をそのまま保持する設計に修正）、この問題を解消した。
   修正前は+/-完全一致率が47.9%（46/96人）だったが、修正後は100%になった

**結論・次のステップへの示唆**: MIN一致率100%・+/-完全一致率100%という結果は、在コート復元
ロジックの信頼性が非常に高いことを示している。この基盤の上に、ラインナップスタッツ（5人組み合わせ
ごとのオン/オフコートスタッツ）を実装する判断材料として十分な精度と言える。ただし今回の検証は
サンプルが4試合（うちOT2試合）のみのため、2026-27シーズンが本格的に始まり試合数が増えた際に、
同じ検証（`npm run validate:oncourt`）を再実行して結果が崩れないか確認することが望ましい。

### 2-7. Phase 5バックフィル調査（2026年8月13日）

**genius_contexts APIの可用性（境界年を確定）**:
- schedule JSON API（`bleague.jp/schedule/?data_format=json&...`）は2016-17〜2025-26の全シーズンで
  問題なく動作する（ScheduleKey収集自体は年代を問わず同じロジックで可能）

**ActionCD1のコード体系（2022-23シーズンで確認・現行シーズンと完全一致）**:

- 2020-21・2021-22シーズンのActionCD1がこの体系と同一かは今回未検証（PlayText突き合わせは

2. **2016-17〜2019-20シーズン**: `game_detail`ページ埋め込みJSON（`_contexts_s3id.data`）を

### 2-8. チーム名変更履歴とTeamIDの安定性調査（2026年8月13日）

バックフィル実装（3層スクレイパー）の前提として、改称したクラブでも`TeamID`が不変かどうかを
実データで検証した。結論: **`TeamID`はクラブ改称をまたいで不変**。バックフィル時にチーム名の
文字列一致に頼る必要はなく、`TeamID`だけで安全にシーズンをまたいだ名寄せができる。

**検証方法**: `bleague.jp/stats/`（成績詳細ページ）のクラブ絞り込みプルダウンは、選択した
シーズンに応じて当時のクラブ名を表示するが、`<option>`の`value`属性（=`TeamID`）はbleague.jp
の内部システムが持つ恒久的なクラブIDであり、シーズンをまたいでも同じ値を保持している。これを
複数シーズンで比較し、さらに実際のgenius_contexts APIレスポンスでも裏取りした。

**確認できた実例**:
- **栃木ブレックス → 宇都宮ブレックス**（2019年7月改称、2019-20シーズン〜適用）: 2016-17
  シーズンのプルダウンでは「栃木」(`value="703"`)、2020-21シーズン以降のプルダウンでは「宇都宮」
  (`value="703"`)。**同一TeamID**。genius_contexts APIは2016-17時点が403で直接検証はできないが、
  bleague.jpの内部クラブIDが不変であることは確認できた
- **サンロッカーズ渋谷 → 東京サンロッカーズ**（2026-27シーズン〜改称予定・発表済み）: 2020-21
  シーズンのプルダウンでは「SR渋谷」(`value="726"`)、現在のプルダウン（2026-27選択時）では
  「東京SR」(`value="726"`)。**同一TeamID**。さらにgenius_contexts APIで2020-21シーズンの実試合
  （ScheduleKey=6007）を取得し、`Game.HomeTeamID`が実際に`"726"`・`Game.HomeTeamNameJ`が
  `"サンロッカーズ渋谷"`であることを直接確認済み（API生データでの裏取り）

**その他の観察事項**:
- 2016-17シーズンのB1クラブ一覧（北海道702・仙台692・秋田693・栃木703・千葉704・A東京706・
  SR渋谷726・川崎727・横浜694・新潟695・富山696・三遠697・三河728・名古屋D729・滋賀698・
  京都699・大阪700・琉球701）は、現行シーズンのクラブ一覧（茨城712・宇都宮703・群馬713・
  A千葉2486・千葉J704・東京SR726・横浜BC694・信州716・神戸718・島根720・広島721・佐賀1638・
  長崎2488等）と比較すると、**単純な改称だけでなく「新規参入クラブ」（佐賀1638・長崎2488・
  A千葉2486等、B1未経験からの昇格）と「B1から陥落・現在は別カテゴリのクラブ」（新潟695等）
  が混在**している。バックフイル実装では「シーズンごとにクラブ一覧が変わりうる」前提で
  `TeamID`をキーにした集計にし、「そのシーズンに存在しないクラブ」を無理に現行クラブ一覧に
  当てはめない設計にする
- 名古屋ダイヤモンドドルフィンズ（名古屋D、`TeamID=729`）とファイティングイーグルス名古屋

**神戸ストークス（3段階改称）の追加調査（2026年8月13日、ユーザー指摘）**: 兵庫ストークス

調査の結果、**この前提は誤りだった**: Wikipediaで確認したところ、西宮ストークスは2016-17

### 2-3. 実装中に判明した追加事項

- **スケジュール一覧のJSON API発見**: `bleague.jp/schedule/` は通常のfetchでは空になるが、
  実際は `?data_format=json&year=...&mon=...&day=...&event=...` というAJAX用JSON APIが
  裏にあり、これで `ScheduleKey` 一覧をHTMLパース不要で取得できることを確認（2章の表に反映済み）
- **`PlayingFlg` の解釈ミスを修正**: 得点・出場時間が記録されている選手でも `PlayingFlg=false`
  になるケースがあった。出場判定は `PlayingFlg` ではなく **`PlayTime !== "DNP"`** で行う

なお「試合成績」セクションには「もっと詳しく見る」リンクがあるが、別リクエストは観測されなかった
ため、**既に取得済みの同一JSON内に追加フィールド（Fastbreak Points等）が含まれ、クリックで表示を
切り替えているだけ**の可能性が高い。12章のプレータイプ内訳スタッツもこのJSON内で解決する可能性がある。

**制約・注意点**（自動更新・無料の要件を守るために厳守）:
- 個人利用の範囲に留める。取得データを再配布・商用利用しない
- リクエスト間隔は最低2〜3秒空ける（サーバー負荷対策）。並列アクセスしない
- 過去シーズン（特に2016-17〜2019-20あたり）はサイトリニューアルでHTML構造が異なる可能性が高い
- サイト構造は将来変わりうるため、スクレイパーはセレクタを1箇所にまとめ、壊れたときに検知・修正しやすい構成にする
- 「スコアチャート」「テキスト速報」は実装前に**必ず実データ（ネットワークリクエスト／HTML構造）を調査**し、
  構造化データとして取得できるか、それとも自前でテキストパースする必要があるかを確認してから設計を確定する
- **試合終了直後のボックススコアは確定値ではない**。公式記録は試合後に修正（誤記訂正・スコアラー修正等）
  が入ることがあり、経験上**試合終了から約1週間後に数値が修正されるケースがある**。「1回取得して終わり」
  ではなく、**直近の試合を一定期間繰り返し再取得し、差分があれば上書きする**仕組みが必須（詳細は8章）

- ラインナップごとのスタッツ
- オンコート／オフコートスタッツ

✅ **基盤の精度検証は完了（2026年8月13日、2-6章）**: 在コート状態の復元ロジック
（`shared/onCourt.ts`）を実装し、手持ちの4試合全件でMIN一致率100%・個人+/-の公式値との

✅ **出場交代バー表示は実装済み（2026年8月13日）**: `shared/onCourt.ts`の`reconstructOnCourt`を

十分に見て取れる）。複数区間を持つ選手を表現する必要があり`recharts`のBar系コンポーネントでは
表現しづらいため、CSS(flexレイアウト＋絶対配置)で自前実装した。506099（延長無し）・505288（OT）
両方で実データ表示を確認済み。ラインナップスタッツは次フェーズ。

✅ **オンコート/オフコートスタッツ（個人）は実装済み（2026年8月13日）**: 個人+/-（公式
`PLUSMINUS`フィールド）は定義上すでに「オンコート純得失点」そのものであるため、`shared/onCourt.ts`
によるPBP再走査は不要と判明（ユーザー指摘）。`scripts/aggregate.ts`で、選手が出場した各試合の
「チーム得失点差」を`teamNetSum`として積算し、`オフコート純得失点 = teamNetSum − 個人+/-合計`
という単純な差分で導出した（シーズン合計・1試合あたり平均の両方をplayers.jsonの`advanced`に追加）。
`src/lib/statDefs.ts`に`onCourtNet`/`offCourtNet`を追加（`source: 'custom'`）。ただし今回のスコープは
個人詳細ページでの確認のみのため、`StatMeta`に`hiddenFromPicker`フラグを新設し、ランキング・比較
ページの選択肢からは除外しつつ用語集には掲載する形にした（RankingsPage/ComparePageは
`PLAYER_STAT_DEFS.filter(d => !d.hiddenFromPicker)`で参照）。

**検証**: 単一試合のみ出場した選手（須藤タイレル拓、チーム最終スコア差-6）でオンコート+13/
オフコート-19（合計-6と一致）、複数試合出場の選手（ドゥシャン・リスティッチ、3試合）でチーム得失点差
合計(-9+9+6=6)からオンコート純得失点15を引いた値がオフコート-9と一致することを手計算で確認。
season全選手のオンコート純得失点合計と個人+/-合計が一致することも確認済み（定義上必然だが実装ミス
がないことの確認として実施）。

✅ **ラインナップスタッツは実装済み（2026年8月13日）**: `shared/onCourt.ts`の`reconstructOnCourt`を
拡張し、個人+/-と全く同じイベント順（tie-break無し・配列の元の並び順を信頼する方式）で、同じ5人が
同時に在コートだった区間を「スティント」として同時に積算するようにした（`LineupStint`型・
`OnCourtReconstruction.lineupStints`）。5人の組み合わせはplayerIdをソートして`,`結合した
`lineupKey`で正規化し、順不同でも同一視する。`scripts/aggregate.ts`の`processLineups()`で
シーズン全試合分をチーム別・lineupKey別に積算し、`data/{season}/lineups/{teamId}.json`に出力する。

**検証**（`scripts/validate-oncourt.ts`を拡張、手持ち4試合＝チーム×試合で8ケース）:
1試合内の「あるチームの全スティント時間の合計」が試合時間（40分＋OT分）と、「全スティント純得失点の
合計」がそのチームの最終得失点差と、それぞれ**8/8ケースで完全一致（100%）**。個人+/-の検証で確立済みの
イベント順ロジックをそのまま流用しているため理論的にも一致するはずだが、実データでも実証した。

**Net Rating（推定）について**: スティント単位の実ポゼッション数はデータ上取得できないため、
チームのシーズン平均ペース（`POSS / (MIN合計/5)`）からスティント時間分を按分して推定ポゼッション数を
算出し、`100 * 純得失点 / 推定ポゼッション数`として計算する近似値（`estimatedNetRtg`）。他のNBA流
アドバンスドスタッツと同様、公式に定義が無いため代替の考え方を採用した位置づけ。

**表示**: `TeamDetailPage.tsx`に「よく使われるラインナップ」セクションを追加。出場時間180秒未満の
組み合わせはサンプルが小さくノイズが大きいため除外し、出場時間の多い上位10組を試合数・出場時間・
得失点差・Net Rating（推定）とともに表示する（実データ確認: 4試合時点で180秒基準だとチームあたり
4〜14組が該当）。閾値・Net Ratingが推定値であることの注意書きをテーブル直下に表示している。
ランキング・比較ページへの追加は対象外（チームごとの個別データのため既存のstatDefs.tsの仕組みには
乗らない）。

`scrape-roster.ts` はcheerioによるHTMLスクレイピングで実装した。
- 一覧: `bleague.jp/roster/?year={year}&club={teamId}&p=&c=&o=random&e=在籍中&tab=1`
  （クラブを絞ると在籍中選手が1ページに収まる。26クラブ分回せば全選手を網羅できる。取れるのは
  playerId・氏名・ポジションのみ）
- 個人: `bleague.jp/roster_detail/?PlayerID={id}`（生年月日・身長／体重・リーグ登録国籍を取得）
- 更新方針: 一覧ページは毎回26クラブ分取得してteamId/teamName/positionを更新（軽量・移籍検知）。
  個人ページは「まだマスタに無い新規選手」だけ追加取得する（身長体重等は変化しないため）。
  これにより2回目以降の実行は新規選手が居ない限り一覧ページの26リクエストのみで完了し、
  日次cronに組み込んでも軽量（8-1章の方針と同じ考え方）。初回のみ在籍中の全選手（300名超）の
  個人ページを新規取得するため15〜20分程度かかる（日次cronに組み込む前に手動でフル実行済み）
  - **teamIdは固定値ではなく毎回上書きされる**: 個人ページを再取得しない既存選手であっても、
    `teamId`/`teamName`は日次cronが走るたびに26クラブの一覧ページ再取得から必ず上書きされる
    （`scrapeRosterMaster()`内で選手が既知でも`entry.teamId = teamId`を毎回実行）。そのため
    移籍が起きても手動更新は不要で、次の日次実行で自動的に反映される。「固定teamIdを避けたい」
    という方針に沿っている。既存選手の所属クラブが前回と変わっていた場合は`movedCount`として
    ログにも出す（移籍検知の可視化）
- **classification（日本人/外国籍/帰化選手/アジア特別枠）は自動判定＋手動上書きのハイブリッド方式
  で実装済み**: `リーグ登録国籍`欄は単一の国名のみで、帰化選手も「日本」表記になり生え抜き選手と
  区別できない（実際に確認: アジア特別枠として知られる韓国出身選手も、通常の外国籍選手と同じ形式で
  母国の国籍が表示されるだけ）。追加調査として以下も確認したが、いずれも該当データは無かった:
  - `club_detail/`ページの「選手情報」タブ（クラブ別ロースター表示。外国籍選手の同時出場人数制限が
    あるため区分表示を期待したが、番号順の単純なリストのみでセクション分け無し）
  - `roster/`一覧ページの絞り込みセレクタ全種類（`club`/`p`/`c`/`o`/`e`）。国籍系は`c`のみで
    値は空/日本/海外の3つだけ。隠しoption等も無い

  - 帰化選手/アジア特別枠: `scripts/lib/playerClassificationOverrides.ts`の手動リスト

    判明した選手をこのファイルに追記していく運用。ネットワーク取得を伴わないため、リストを
    更新すれば次回`scrape-roster.ts`実行時に全選手へ反映される（新規選手の個人ページ取得とは
    独立して毎回再計算される）
  - **2026-08-13時点でユーザー提供リストを反映済み**: B.LEAGUE全クラブ（B.PREMIER以外含む）の

## 6. 集計ロジック（スタッツ計算式）

### 基本スタッツ
PTS, OREB/DREB/REB, AST, STL, BLK, TOV, PF, FG(M/A/%), 3P(M/A/%), FT(M/A/%), MIN
→ シーズン合計・平均（Per Game）、スタメン/ベンチ別、国籍区分別、シチュエーション別（時期・勝敗・直近N試合）
にフィルタして再集計できる設計にする

### アドバンスドスタッツ（Bリーグ公式定義を優先し、NBA流で補足）

方針: **Bリーグ公式の「スタッツ用語解説」（`https://www.bleague.jp/glossary/`）に定義がある
項目はその式をそのまま採用する**。公式に定義がない項目のみ、NBA/Basketball-Reference流の
一般的な式で補う。これにより、放送や公式サイトで見る数字とズレない値を出せる。

**Bリーグ公式の定義（確認済み・採用）**:
- **POSS（ポゼッション）**:
  `0.5 × ((FGA + 0.4×FTA − 1.07×(OR/(OR+相手DR))×(FGA−FGM) + TO)
        + (被FGA + 0.4×被FTA − 1.07×(被OR/(被OR+DR))×(被FGA−被FGM) + 被TO))`
  → 自チーム・相手チーム双方の推定ポゼッションを平均する精密な式。**これまで実装していた
  簡易式（`FGA - OREB + TOV + 0.44*FTA`）より精緻なので、公式のこの式に置き換える**
  （すでに実装済みのORtg/DRtg/Paceの数値に影響するため、formulas.tsの修正が必要）
- **PACE**: `試合時間 × (POSS + 被POSS) / (2 × (プレイタイム / 5))` → 既存実装と一致（確認済み）
- **EFG%**: `(FGM + 0.5×3PM) / FGA` → 既存実装と一致（確認済み）
- **TS%**: `PTS / (2 × (FGA + 0.44×FTA))` → 既存実装と一致（確認済み）
- **OFFRTG/DEFRTG/NETRTG**: 100ポゼッションあたりの得点／失点／得失点差（＝100×PTS/POSS。
  上記の公式POSSを使う）
- **EFF（貢献度）**: Bリーグ公式が定義する総合指標。**Game Score（NBA流の代替案）の代わりに
  こちらを採用**する。**実装・検証済み**（`formulas.ts`の`eff()`。GeniusAPI生データに含まれる
  公式EFF値と、1試合53人全員で完全一致を確認済み。この検証方法により、個人単位の被ファウル数
  (FD)・被ブロック数(BSR)がPBPから正しく取得できることも同時に確認できた）
  - 2020-21シーズン以降: `(PTS+AS+BS+ST+FD+TR) − (TO+BSR+F+TF) − (2FGA−2FGM) − (3FGA−3FGM) − (FTA−FTM)`
  - 2019-20シーズン以前: `((PTS+TR+AS+ST+BS) − (2FGA−2FGM) − (3FGA−3FGM) − (FTA−FTM) − TO) / 試合数`
  - ⚠️ **年度で式が異なる**ため、Phase 5の過去シーズンバックフィル時にシーズンで式を切り替える
    実装にすること（`aggregate.ts`に分岐は用意済み。現状は2026-27シーズンのみ扱っているため
    新しい式しか使われていない）
  - ✅ **修正済み（2026-08-16）: テクニカルファウルの重み付け漏れ（TF項）を追加**。上記「1試合
    53人全員で完全一致」の検証はテクニカルファウルが低頻度事象のため、たまたま出現しなかった
    1試合でのみ行われたものだった。14-6章のB.ONE多試合検証（35試合・768人）で
    「テクニカルファウル(`ActionCD1=24`)を記録した選手は公式EFF値が再計算値より常に1小さい」
    というズレを発見し、B.PREMIER側の過去データ（2020-21〜2025-26の6シーズン・60試合・
    1263人）でも同じズレが再現することを確認した。ボックススコアの`FOUL`（=F）フィールドは
    テクニカルファウルも通常のパーソナル/オフェンスファウルと同じ「1」として数えるが、公式EFFは
    テクニカルファウルを2倍の重みで減点している（＝`F`に加えてテクニカルファウル数`TF`を
    もう1回分追加で引く必要がある）。`shared/formulas.ts`の`eff()`に`technicalFouls`
    （`EffTotals`の新フィールド）を追加し、`scripts/aggregate.ts`に
    `countTechnicalFouls()`（`PlayByPlays`の`ActionCD1=24`を`PlayerID1`単位で、
    `ActionCD1=20/21/24`を`TeamID`単位で集計）を新設して修正した。選手個人はActionCD1=24
    （選手個人のテクニカルファウル）のみを対象とし、HC/ベンチテクニカル（20/21）は選手に
    紐付かないため個人側には加えない。チーム集計は20/21/24の合計を対象とする（チームの
    `Category=3`行の`FOUL`はチームに帰属する全種別のファウルを合算した値のため）。
    修正後、B.ONE35試合（768人）・B.PREMIER60試合（1263人、2020-21〜2025-26の6シーズン
    横断）の両方でEFF完全一致率100%を達成した。**B.PREMIER全10シーズン
    （2016-17〜2025-26）を`npm run aggregate`で再集計済み**（2019-20以前の式にはF項自体が
    無いため、この修正の影響を受けるのは2020-21シーズン以降のみ）
- **POSS/PACE/ORtg/DRtg/NetRtg/Usage%/FTR/ORB%: 実装・配線済み**（`aggregate.ts`の出力・
  ランキング/比較/グロッサリーページまで反映済み）
  - **POSS集計の注意点（実装で判明）**: シーズン合計の基本カウント統計に公式POSS式（比率項を
    含む）を再適用すると、非線形性により誤差が出ることが判明。正しい方法は、**GeniusAPI生データの
    各試合のチーム行に既に入っている公式POSS値をそのまま試合ごとに合算する**こと（式を
    再計算しない）。実データで自チーム/相手チーム行が同一値になることも確認済み
  - **Usage%の検証**: GeniusAPI生データの個人行に`USG`フィールドが実在し、実装したNBA流の式と
    完全一致することを確認（EFFのときと同様の検証パターン）
- **+/-（個人単位）**: 「その選手が出場していた時間帯のチーム全体の得失点差」。Bリーグ公式が
  個人スタッツとして定義している。これは**ティアC「ラインナップスタッツ」「オンコート/
  オフコートスタッツ」よりずっと単純**（5人の組み合わせ追跡が不要で、個人の出場区間だけ
  追えばよい）。選手交代のActionCD1コード確認（11章）が前提だが、確認でき次第、ラインナップ
  系より優先して着手する価値がある
- **%-share系（公式定義あり、box scoreのみで算出可・tier A）**: `%PTS`, `%FGM`, `%FGA`,
  `%3PM`, `%3PA`, `%FTM`, `%FTA`, `%OREB`, `%DREB`, `%REB`, `%AST`, `%TOV`, `%STL`, `%BLK`,
  `%BLKA`, `%PF`, `%PFD` — いずれも「個人の数値／チームの数値」のシンプルな比率。**12章の
  「AS%」の扱いを訂正**: Bリーグ公式の`%AST`（個人アシスト数／チームアシスト数）はbox score
  のみで算出できるtier A。一方、ユーザーが元々挙げていたチームレベルの「AS%＝FG成功のうち
  アシストが付いた割合」は別概念で、こちらは引き続きショット単位のアシストフラグが必要（tier B）
- **得点内訳系（公式の略称、12章のプレータイプ内訳と対応）**: `PITP`(Points In Paint),
  `FBPS`(Fastbreak Points), `2NDPTS`(Second Chance Points), `PTSOFFTO`(Points Off
  Turnovers) — いずれも公式に定義された実在の指標であることを確認（`Summaries`に含まれる
  ことは2-2章で確認済み）。**`Summaries`内の実フィールド名との対応は2026-08-17に確定済み**
  （genius_game_new2208.jsのソースコードで「ゲームスコア/試合成績」欄のレンダリング処理を
  直接確認。ActionCD1・TEAM/COACHES欄の特定と同じ手法。詳細は12章末尾）:
  `HomeTeamPT2IN`/`AwayTeamPT2IN`=PITP（表示ラベル "Points in the Paint"／
  「ペイントエリア内での得点」）、`HomeTeamPTFB`/`AwayTeamPTFB`=FBPS（"Fast Break Points"／
  「ファストブレイクポイント」）、`HomeTeamPT2ND`/`AwayTeamPT2ND`=2NDPTS（"Second Chance
  Points"／「セカンドチャンスポイント」）、`HomeTeamPTPFT`/`AwayTeamPTPFT`=PTSOFFTO
  （"Points From Turnover"／「ターンオーバーからの得点」。フィールド名`PTPFT`からは意味が
  読み取れなかったが、ソース確認により確定した）
- **BSR（被ブロック）**: 公式に個人・ボックススコア両方で定義された指標

**Bリーグ公式に定義がない項目（NBA流で補足・そのまま採用）**:
- **Usage%**: `100 * ((FGA + 0.44*FTA + TOV) * (TeamMIN/5)) / (MIN * (TeamFGA + 0.44*TeamFTA + TeamTOV))`
  → Bリーグ公式に相当する定義なし。NBA流をそのまま採用
- **FTR（フリースローレート）**: `FTA / FGA` → 公式に定義なし、NBA流を採用
- **ORB%（オフェンスリバウンド率）**: `100 * TeamOREB / (TeamOREB + OppDREB)` → 公式のPOSS式
  内に同じ考え方の項があるが、独立した指標としては定義されていない。NBA流を採用
- PERはリーグ全体係数が必要で複雑なため引き続き後回し候補

**未確認・公式に見当たらなかった項目**: デッドTOV／ライブTOV（ターンオーバーの種別分け）は
Bリーグ公式の用語解説には存在しない。ユーザー独自の集計軸と思われるため、12章の通りtier B
（ActionCD1のイベント種別分類に依存）のまま進める。

## 8. 自動更新フロー（GitHub Actions）

### 8-1. 新規試合の取得と、既存試合の再チェック（スタッツ修正対応）

公式記録は試合後に修正が入ることがあり、経験上**試合終了から約1週間後に数値が修正される
ケースがある**。そのため毎回の実行で「新規試合の取得」だけでなく「直近試合の再取得・差分検知」
を必ず行う。

- **対象範囲**: `meta.status` が `"watching"` の試合（＝直近の一定期間内の試合）は毎回再取得する
- **監視期間**: 試合終了から**14日間**を再チェック対象とする（「約1週間で修正される」に対し、
  検知漏れを防ぐため約2倍のバッファを確保。日数は運用しながら調整可能なパラメータにする）
- **監視終了**: 監視期間を過ぎたら `status` を `"final"` にして再チェック対象から外す
  （スクレイピング量を抑えるため。ごく稀に14日超で修正が入った場合は手動で個別再取得できる
  コマンドも用意しておく）
- **差分検知**: 新しく取得したボックススコアと保存済みJSONを比較し、値が変わっていれば
  - 該当 `games/{scheduleKey}.json` を上書き、`meta.lastChangedAt` と `revisionCount` を更新
  - その試合が属するシーズンの `teams.json` / `players.json` / `standings-history.json` を
    **必ず全量再計算する**（生データが正、集計は都度生成し直す設計のため、部分的な差分反映は
    せず毎回作り直すことで修正の反映漏れを防ぐ）
  - 変更内容は簡易ログ（例: `data/changelog/{season}.log`）に追記し、後から「いつ何が修正されたか」
    を追えるようにしておく（任意だが推奨）

### 8-2. スケジュール収集の頻度（フル収集 vs 日次の軽量チェック）

実装検証の結果、シーズン全体のスケジュール一覧を1回フル収集すると約500リクエスト・
2.5秒間隔で約20分かかることが判明した。これを毎日のcronにそのまま含めると実行時間・
サーバー負荷の両面で無駄が大きいため、以下のように分離する。

- **フル収集**（`scrape-schedule.ts` の全件モード）: シーズン開幕時、または延期・日程変更が
  疑われるタイミングでのみ、手動（`workflow_dispatch`）または週1回程度の別ジョブとして実行
- **日次cron**: 直近数週間分（前後2週間程度）のスケジュール・試合結果のみを軽く再チェック。
  対象範囲は8-1章の「14日間watching」の仕組みとほぼ同じなので、同じジョブ内で統合してよい

### 8-3. データサイズへの対応（実装済み・2026年8月13日）

1試合分の生データ（PlayByPlaysの座標込み）は約700KBあり、フルシーズン500試合超で350MB前後に
なる見込み。**Phase 5の過去シーズン一括バックフィル前に方針を決めて実装した**（後から大量データを
圧縮し直すのは無駄なため）。

**実装方針**: 全JSONを `.json.gz` として保存する。`scripts/lib/storage.ts`の`writeJson`/
`readJson`/`writeGameFile`/`readGameFile`/`readAllGames`に圧縮・伸長を透過的に組み込み、
呼び出し側（`aggregate.ts`・`scrape-boxscore.ts`等）は従来通り拡張子`.json`のパスを渡すだけで
よい（実体ファイル名への`.gz`付与・削除は`storage.ts`内に閉じている）。フロントエンドは
`src/lib/data.ts`の`fetchJson`で`.gz`付きURLを取得し、`DecompressionStream` APIでその場展開する。

**実データでの圧縮率**: 既存data/配下（191ファイル・5.24MB）を`scripts/migrate-gzip.mjs`で
一括変換した結果、0.32MBまで圧縮（**93.8%削減**）。想定通りの圧縮率だった。

⚠️ **実装時に発見した環境差異**: Vite開発サーバー（dev server）は`.json.gz`ファイルを
`Content-Encoding: gzip`ヘッダ付きで返し、ブラウザの`fetch`自体が透過的に展開してしまう
（この場合`res.body`は既に展開済みの生JSONで、追加で`DecompressionStream`にかけると
`TypeError: Failed to fetch`になる）。一方GitHub Pages等の素の静的ホスティングはそのような
透過展開をしないため、レスポンスは圧縮バイト列のまま届く想定。`fetchJson`はレスポンスの
`Content-Encoding`ヘッダの有無を見て、既に展開済みならそのまま`res.text()`、そうでなければ
`DecompressionStream`で展開する、という両対応の実装にした（本番ビルド`dist/`には実際に
gzip圧縮されたファイルが出力されることを`file`コマンドで確認済み）。

### 8-4. GitHub Actions ワークフロー（イメージ）

```yaml
on:
  schedule:
    - cron: "0 18 * * *"   # 毎日JST3時（UTC18時）。試合日程に合わせ調整
  workflow_dispatch: {}
jobs:
  update:
    steps:
      - checkout
      - 直近数週間分のスケジュール再チェック（8-2参照。フル収集は含めない）
      - 新規試合のスクレイピング（未取得試合分のボックススコア・PBPを取得）
      - 直近14日以内の"watching"試合を再取得し、差分があれば上書き（8-1参照）
      - 監視期間を過ぎた試合を"final"に更新
      - 集計再計算（games/*.json全体からteams/players/standings-historyを再生成）
      - 差分があればcommit & push
```
- シーズンオフはcron停止 or 差分なしで実質何もしない
- 過去シーズンのバックフィルは通常運用のcronとは別の一回限りのスクリプトとして、
  サーバー負荷をかけすぎないようゆっくり実行する（バックフィル時点で試合終了から
  14日以上経過している試合は最初から`status: "final"`として取り込んでよい。8-3章の
  圧縮方針もこのタイミングで適用する）

  Sideに紐づかない一貫した値ではなかった。X・Y両方を反転する（180度回転）ことで、同一選手・

**個人+/-実装メモ（2026年8月13日）**: 当初はPlayByPlaysのActionCD1=86/87（選手交代イン/アウト）
から在コート選手を復元し、得点イベントのたびに加減算する自前再構築を想定していたが、着手前に

存在し、かつ値も妥当（DNP選手は0、出場選手は試合展開と整合する符号・大きさ）であることを確認した。
POSS/EFF/USGのときと同じ「まず生データに公式フィールドが無いか確認してからロジックを自作する」
という方針が功を奏し、PBP再構築・在コート人数検証・MIN一致検証は不要になった。この経緯は
今後似た指標（例: ラインナップスタッツ）を検討する際も、まず生データの全フィールドを確認してから
着手する、という教訓として残す。

島根スサノオマジック等）で検証し、実際のロゴ配色と一致することを確認済み。

**獲得タイトル履歴（`scripts/scrape-club-honors.ts`）**: 当初はbleague.jpのクラブ詳細ページ
（`club_detail/?TeamID=`）にシーズン別の内訳があると想定していたが、実際には**累計回数のみ**
（例:「Bリーグチャンピオンシップ優勝：3回」）でseason情報が無いことが調査で判明。加えて、この
累計カウンター自体が**直近シーズンの反映が遅れる**ことも発覚した（長崎ヴェルカの2025-26年間
優勝が、B.MAGAZINE記事では確認できるのにカウンターには未反映だった実例）。このため3種類の
データソースを使い分ける方式に切り替えた:
1. **年間優勝**（Bリーグチャンピオンシップ優勝）: このプロジェクトが既に保存済みの試合データ
   （`data/{season}/games-summary.json`）から、プレーオフの中で最も日付が新しい試合の勝者を
   ファイナル決着とみなして機械的に導出。bleague.jpへの追加アクセスは不要
2. **地区優勝**: `bleague.jp/standings/?year={年}&tab=1`（B1タブ）の地区別テーブルを取得し、
   各地区の1位チームを地区優勝とする。**地区制自体が毎シーズン変動している**ことをWeb調査で
   発見したため（2016-17〜2019-20:東/中/西3地区、2020-21〜2021-22:東/西2地区、2022-23〜
   2024-25:再び東/中/西3地区、2025-26:東/西2地区。所属クラブの組み合わせも毎シーズン変動）、
   このプロジェクトが持つ`divisions.ts`（2026-27時点のマスタ）はそのまま過去シーズンに
   適用できず不採用とし、シーズンごとに実際のページを取得して判定する方式にした
3. **国際大会**（BCLアジア・EASL・前身のFIBAアジアチャンピオンズカップ）: 該当クラブが少数
   （4クラブ・5件）なため、Web検索で複数の一次情報（bleague.jp公式ニュース・B.MAGAZINE・
   バスケットボールキング等）を突き合わせてseason/年を確定し、スクリプト内に手入力した

天皇杯優勝・B2年間優勝・B2地区優勝はユーザー依頼のスコープ外（年間優勝／地区優勝／国際大会の
B1・B.PREMIER実績のみ）として意図的に除外。妥当性チェックとして、上記1〜3で生成した結果を
クラブ詳細ページの累計回数カウンターと突き合わせ、長崎ヴェルカ（カウンター側が未反映という
既知の理由）を除く全クラブで件数が一致することを確認済み。

**年間優勝の導出過程で発見したデータ欠落は根本解決済み（11章に詳細）**: 2020-21シーズンの

ScheduleKeyを特定して通常のスクレイパーで取得・保存し、2020-21シーズンを再集計して解消した

（例: ScheduleKey=505741 中谷選手、505870 アギラール選手・モッチ選手等、複数試合で再現）。
ボックススコアの`FOUL`（ファウル数）フィールドはテクニカルファウルも通常のパーソナルファウルと
同じ「1」としてカウントするが、公式`EFF`はテクニカルファウルを**より重く（実質2として）
減点している**らしいことが数値から逆算できる（`FOUL`をそのまま使う単純な式では説明できない
差分が、テクニカルファウルの発生数と常に一致した）。

この発見は**B.ONE固有の問題ではない可能性が高い**点に注意: DESIGN.md 6章の元々のEFF実装検証は

13件＝1試合あたり0.37件）のため、たまたま検証時の1試合に出現しなかっただけの可能性が高い。
**B.PREMIER側でも同じ式を使っている以上、同じズレが潜在している可能性がある**。実装のブロッカー
ではない（98.3%は一致しており、B.ONE固有の障害ではないため）が、次にEFF計算式を触る際は
テクニカルファウルの重み付けを`formulas.ts`側で見直す価値がある発見として記録しておく。

**結論**: B.ONEは35試合・25,931件というレギュラーシーズン全体を代表する規模のサンプルで、
API取得成功率100%・フィールド欠落0件・選手交代モデルの一貫性100%・ショット座標の異常値0件を
確認した。EFF計算式の小さな乖離（テクニカルファウルの重み付け）が見つかったため、B.ONE実装に
進む前にこの修正を先に行うことにした（14-7章）。

### 14-7. EFF計算式のテクニカルファウル重み付け修正（2026-08-16）

14-6章で見つかったEFF不一致13件について、公式値との差分から重み付けの規則性を逆算した。

**逆算の手順**: 差分が生じた13人全員で「再計算値 − 公式値 = +1」と完全に一定だった。
`PlayByPlays`を個別に追跡すると、この13人は全員が該当試合中に自分自身の`ActionCD1=24`
（選手個人のテクニカルファウル）を**ちょうど1回だけ**記録していた。ボックススコアの`FOUL`
フィールドはテクニカルファウルも通常のパーソナル/オフェンスファウルと同じ「1」として
カウントしているため、`FOUL`をそのまま「F」として使う式では公式値を再現できない。
「テクニカルファウル1回につきFの実効値をもう1追加する（＝通常ファウルの2倍の重みにする）」
という規則を当てはめると、全13件で公式値と完全に一致した（例: ScheduleKey=505741
上村選手はテクニカルファウル1回のみでFOUL=1、公式EFF=9。`F`を1のまま計算すると再計算値は
10になり不一致だが、`F`を2として計算すると9で一致する）。

**HC/ベンチテクニカル（ActionCD1=20/21）の扱い**: DESIGN.md 2-2章の既存確認どおり、これらは
選手個人に紐付かず`Category=2`（チーム発生イベント行）の`FOUL`にのみ計上される。そのため
個人EFFの補正対象は`ActionCD1=24`のみとし、20/21は含めない。一方チーム集計（`Category=3`
「真のチーム合計行」）の`FOUL`はチームに帰属する全ファウルの合計（`Category=1`の個人分＋
`Category=2`のチーム発生分）であるため、チーム単位のEFF補正では20/21/24の合計を対象にする
必要がある（同一試合で実際にCategory=3のFOULがCategory=1の合計と一致することを確認済み。
コーチ/ベンチテクニカルが発生した試合ではCategory=3側にその分が上乗せされる）。

**実装**（`shared/formulas.ts`・`scripts/aggregate.ts`）:
- `EffTotals`（`formulas.ts`）に`technicalFouls`を追加し、`eff()`の2020-21以降の式を

既存のコメント（B.PREMIER向け）が、B.ONE対応でも構造として引き継がれているかを再確認した。

**現状**: `teamDivision(teamId, category)`は`season`引数を持たない。カテゴリごとに単一の
スナップショット（`TEAM_DIVISIONS`＝B.PREMIER 2026-27シーズン基準、`ONE_TEAM_DIVISIONS`＝
B.ONE 2026-27シーズン基準）を参照するだけの実装であり、**「シーズンに応じて正しい地区分けに

新たに生まれた欠陥ではなく、既存の技術的負債がそのままB.ONE側にも及んでいる状態、という
位置づけである。

**将来の対応方針（未着手・設計メモ）**: 過去シーズンの地区別集計を正しく行いたくなった時点で、
`TEAM_DIVISIONS`・`ONE_TEAM_DIVISIONS`という「カテゴリ別・単一スナップショット」の構造を、
`Record<Category, Record<Season, Record<TeamID, Division>>>`のような「カテゴリ×シーズン×
チームID」の3次元マスタに拡張する案が有力。B.PREMIER・B.ONE（将来的にはB.NEXTも）を同じ
仕組みで一括管理できる。ただし所属クラブ・地区体系はシーズンごとに実ページを確認して
手動整備する必要がある（12章末尾の`bleague.jp/standings/?year={年}&tab={1|2|3}`を都度
確認する運用になる見込み）ため、着手は「過去シーズンの地区別集計を実際に使う段になってから」
で問題ない。現時点では急いで拡張する理由が無いため、次のB.NEXT対応時に改めて検討する。

## 15. Points Off Turnovers（PTSOFFTO）の個人単位算出（2026-08-17）

12章のチームスタッツ項目カタログでは「プレータイプ内訳」の一つとしてPTSOFFTO（ターンオーバーから
の得点）は`Summaries`のチーム単位フィールド（`HomeTeamPTPFT`/`AwayTeamPTPFT`）から取得済み
（tier A）としていたが、個人単位の内訳は未着手だった。個人単位で算出できないか調査・実装した。

### 15-1. ActionCD1のターンオーバーコード確認

DESIGN.md 2-2章の確定コード表には含まれていなかったが、14-6章（B.ONE多試合検証）の過程で
`ActionCD1=13`＝個人のターンオーバー、`17`＝チーム発生のターンオーバー（`Category=2`相当、
個人に紐付かない）であることを既に確認済みだった。実データ（`data/2025-26/games/504728.json.gz`）
でも`PlayText`「ターンオーバー」で裏付けた。`TeamID`・`PlayerID1`・座標(`X`/`Y`/`AreaCD`)も
同梱されている。

### 15-2. 状態機械によるポゼッション復元は不採用（62%一致どまり）

当初は`shared/onCourt.ts`と同様の設計思想で、PlayByPlaysを時系列（`elapsedSeconds`昇順）で
1回走査し、「ターンオーバー直後に始まった相手チームのポゼッション」を状態機械
（`currentOffense`＝現在ボールを保持しているチーム、`turnoverFlag`＝そのポゼッションが
ターンオーバー起因か）で追跡する実装を試みた。オフェンスリバウンドは同一ポゼッションの継続、
ディフェンスリバウンドは新規ポゼッションの開始として扱い、「クリーンな得点の後は相手ボールに
移った旨の明示的なイベントが無い」問題には、ボールを保持する行動（シュート試投・FT試投・
ターンオーバー）のTeamIDがcurrentOffenseと食い違った時点で暗黙にポゼッション交代とみなす
補正を入れた。

検証（`scripts/validate-points-off-turnovers.ts`、公式`Summaries`のPTPFTとの突合）の結果、
2025-26シーズン802試合・1596チーム×試合で**一致率62%（990/1596）**にとどまり、不採用とした。

### 15-3. 発見: PlayText自体に公式判定タグが埋め込まれていた

不一致の1試合（ScheduleKey=504730）を手動トレースしたところ、得点イベントの`PlayText`に
公式が既に判定した結果が直接埋め込まれていることを発見した。例:
`"#21 ジェイコブセン 2Pシュートインサイドペイント○  ジャンプショット
  ポインツオフターンオーバーセカンドチャンス (4点)"`
のように、得点が「ターンオーバーからの得点」に該当する場合、`PlayText`に
**"ポインツオフターンオーバー"**というタグが付与されている。既存の`PT2IN`（PITP）・
`PT2ND`（2ND PTS）・`PTFB`（FBPS）が個人単位のBoxscoreRowフィールドとして存在するのと
同じ仕組み（bleague.jpのバックエンドが判定した結果を個人行にも反映している）とみられる。

このタグを持つ得点イベント（`ActionCD1`∈{1,3,4,7}＝2P/3P/FT成功）の得点を選手単位で
合算するだけで、公式`Summaries`の値と完全に一致することを確認した
（状態機械による自前のポゼッション復元は不要と判明し、`shared/pointsOffTurnovers.ts`の
実装をタグ集計方式に全面的に書き直した）。

**表記ゆれの発見**: タグの末尾の長音符「ー」は、後ろに別のタグ（"セカンドチャンス"等）が
続く場合に脱落する（例:
"ファストブレイクポインツオフターンオーバセカンドチャンス"、"ー"無し）。この表記ゆれに
気づかず末尾の長音符ありで完全一致検索していたところ2025-26シーズンの一致率が89.3%
（1426/1596）にとどまっていたが、タグ判定を「末尾の長音符を含めない」形に修正したところ
**100%一致（1596/1596）**になった。

- **バスケットカウント（アンドワン）**: 既知の`ActionCD1=16`がそのままマーカーとして機能
  （15-3章の調査で挙動も裏付け済み）
- **アシストからの得点**: アシストイベント（`ActionCD1=12`）自体には、どの得点に紐づくかを
  示すタグが無い。得点イベント側にも「誰にアシストされたか」の記載が無いため、PTSOFFTOのような
  「タグを数えるだけ」の単純化はできず、アシストイベントと直後の得点イベントの時間的近接性から
  推測する別ロジックが必要
- ✅ **新規に特定**: `ActionCD1=25`＝**アンスポーツマンファウル**（`PlayText`「#N 選手名
  アンスポーツマンファウル」、14-3章で既出）、`ActionCD1=26`＝**ディスクォリファイングファウル**
  （`PlayText`「#N 選手名 ディスクォリファイングファウル」）。26は2章末尾で「未確認」として
  残っていたコードの一つで、今回2025-26〜2022-23の4シーズン・3019試合中6件の実データで
  裏付けが取れた。B.LEAGUE/FIBA用語では"フレグラント"という語自体は使われず
  「アンスポーツマンファウル」と表記される（16章参照：この呼称は2026-27シーズンから
  FIBA競技規則改正の影響を受ける見込み）

**実装（2026-08-18）**: `src/lib/boxscoreAggregate.ts`の`buildMiscEventCounts()`が、
選択中の期間範囲でフィルタ済みのPlayByPlaysから4項目（`dunks`/`basketCounts`/
`unsportsmanlikeFouls`/`disqualifyingFouls`）を選手ごとに集計し、`buildPlayerBoxscores()`が
`BoxscoreCounts`へ事後的にマージする（ptsOffTov・paint2m等と同じパターン）。チーム合計行は
`BoxscoreTeamPanel`側で選手ごとの値を合算する（BoxscoreRowのCategory=3行にはこれらの
フィールドが無いため）。ボックススコアのMiscタブに列（DUNK/AND1/UFOUL/DQFOUL）として追加した。
UFOUL/DQFOULは低頻度かつ「多い方が良い」わけではない指標のため、DUNK/AND1とは異なりトップ値
ハイライトの対象からは外した（ほぼ全選手が0になり、ハイライトすると該当者以外の全員が
ハイライトされてしまうため）。2018-19シーズン（legacy取得）でもダンクタグが実データに
存在することを確認済みで、シーズン制約は設けていない。実データで動作確認済み
（2025-26シーズン試合504728でダンク数・アンドワンが手動集計値と完全一致、
2025-26シーズン試合505021でディスクォリファイングファウルの表示を確認）。

## 17. 個人単位ORtg/DRtg/NetRtg/PACE（2026-08-17、2026-08-18に算出式を全面差し替え）

NBA.com/Basketball-Referenceの個人ページにある「この選手が出場中のチームのORtg/DRtg」と
同じ考え方の指標。公式にこの値は提供されていないため自前で算出する。

**2026-08-18更新**: 当初は在コート区間（PlayByPlaysベース）から独自算出していたが、
ユーザー指示により**Dean Oliver氏の公式計算式**（Basketball-Reference準拠、
https://www.basketball-reference.com/about/ratings.html ）に全面差し替えた。PACEのみ
在コート区間ベースの旧実装を継続する（この式の対象外のため）。旧実装（在コート区間ベースの
ORtg/DRtg算出、17-1〜17-3節の当時の内容）は本節の履歴として下記に置き換える形で削除した。

### 17-1. 算出式（Dean Oliver方式）

`shared/formulas.ts`の`individualOffRtg`/`individualDefRtg`/`individualPointsProduced`が、
基本ボックススコア（個人・自チーム合計・相手チーム合計）のみから算出する（PlayByPlaysには
依存しない）。式はBasketball-Referenceの公式定義をそのまま実装した（詳細な中間変数は
コード内コメント参照）。Team_Possessionsには既存のPOSS推定値
（`estimatedPossessions()`、自チーム視点の推定値）をそのまま渡す。

分母が0になりうる箇所（FGA=0・FTA=0・Team_FGA=Player_FGA等）はすべて`safeDiv()`でガードし、
0を返す＝その項の寄与を0にする。出場時間0の選手、またはORtgの分母TotPoss（推定得点機会数）が
0以下の選手は「算出不能」としてundefinedを返す（0点ではなく「-」表示にするため）。

PACEのみ引き続き`shared/onCourt.ts`の在コート区間ベース（`computeOnCourtRatings()`）を使う
（`buildPossessionStartEvents()`によるPlayByPlaysベースのポゼッション区切り検出、詳細は
Git履歴の旧版参照）。

### 17-2. 数値不安定性の発見と対処（qAST・出場時間ガード）

実データ検証で、qAST（アシスト貢献の重み）の第2項の分母
`(Team_FGM/Team_MP)*MP*5 - FGM` が、出場時間が短い選手でたまたま0に極めて近い値
（0.002等）になるケースを発見した。`safeDiv()`は完全な0のみガードするため暴走を防げず、
2025-26シーズン実データで瀬川琉久選手（千葉ジェッツ、2:35出場・FGM=2・AST=0）の
PProdが**-1551.2**という非現実的な値になり、チーム合計PTS=85に対しPProd合計が-1474.4に
なる事例を検出した（Basketball-Reference公式の計算式自体に内在する既知の弱点であり、
実装上の転記ミスではない）。

ユーザー承認の上、以下2段階の対策を施した:

1. **出場時間ガード**（`MIN_MINUTES_FOR_INDIVIDUAL_RATING = 4`）: 出場時間4分未満の選手は
   ORtg/DRtg/NetRtgとも「算出不能」（undefined）にする。2025-26シーズン全試合の実データで
   バケット別に|PProd|の最大値を確認したところ、1〜4分では55.6〜1551.2と暴れるのに対し、
   4分以上では39.3以下に収まることを確認した上で閾値を決定した
2. **qASTのクランプ**（`[-0.5, 2]`）: 4分以上の選手でも同じ分母近傍0の暴走が起こりうる
   ことを追加検証で確認した（例: 5:11出場の選手でORtg=-984.5）ため、qAST自体を
   妥当な範囲にクランプする追加の安全策を入れた。qASTは本来「アシストされた割合」を表す値で
   2025-26シーズン実データ（出場10分以上の選手13,631人分）ではp1=0.32・中央値0.71・
   p99=1.17・最大3.13に収まっており、この分布を踏まえて`[-0.5, 2]`とした

対処後、同シーズンの検証で瀬川琉久選手の事例を含む全ての極端な外れ値が解消したことを確認した
（17-3節の検証結果参照）。

### 17-3. 検証

Dean Oliver氏の設計上、あるチームの全選手のPProd（個人の得点貢献推定値）の合計は、
そのチームの実際の得点（PTS）に近い値になるはず（完全一致はしないが大きく乖離しないはず）
という性質を使い、`scripts/validate-oliver-ratings.ts`で間接検証した
（`node --experimental-strip-types scripts/validate-oliver-ratings.ts --season 2025-26`）:

| シーズン | チーム×試合数 | PProd平均絶対誤差 | 平均相対誤差 | ±5点以内 | ±10点以内 |
|---|---|---|---|---|---|
| 2025-26 | 1596 | 4.59点 | -5.7%（系統的にやや過小） | 64.3% | 98.1% |
| 2021-22（`OFFRTG`/`POSS`フィールド無しのシーズン） | 1236 | 4.13点 | -5.2%（同上） | 72.8% | 98.4% |

いずれのシーズンも同程度の精度で、系統的にやや過小（Dean Oliver方式で一般的に知られる
傾向）という結果になった。**基本ボックススコアのみで計算できるため`coverage`によるシーズン
制約は不要**で、公式`OFFRTG`/`POSS`フィールドが存在しない2021-22シーズンでも2025-26シーズンと
同等の精度で動作することを確認した（ORtg/DRtgの外れ値チェックも、対処後は
2025-26シーズンでmin=-39.4/max=300.0・平均107.2、2021-22シーズンでも同様の妥当な範囲に収まった）。

**個別事例**（試合503902、2024-25シーズン、宇都宮ブレックス vs 琉球ゴールデンキングス）:
鵤誠司選手（1:13出場・0得点）はMIN_MINUTES_FOR_INDIVIDUAL_RATING未満のためORtg/DRtg/NetRtg
とも「-」表示。他の選手は全員妥当な範囲の値（例: D.J・ニュービル ORtg=115.0・DRtg=118.3、
荒川颯 ORtg=209.6）になることを確認した。

### 17-4. UI反映

試合詳細ページのアドバンスドタブに、既存のPOSS/PACE/ORtg/DRtg/NetRtg列（チーム合計行専用
だった列）をそのまま流用する形で反映した。チーム合計行は従来通りチームレベルの値、選手行は
個人単位の値を表示する（PACEのみ在コート区間ベースのため試合全体選択時・coverage==="full"の
シーズンのみ、それ以外は「-」）。ORtg/DRtg/NetRtgは選択中の期間範囲（試合/Q別/前後半）の
BoxscoreCountsからその都度算出するため、Q別選択時にも追従する（PACEとは異なりシーズン制約も無い）。
最低出場時間フィルタ（`minMinutesForRanking`と同種の仕組み）は、ランキングページとは異なり
ボックススコアでの単純表示のため不要と判断した（ユーザー確認済み）。17-2節の出場時間ガードが
実質的に同じ役割を兼ねている。

### 17-5. 実装

- `shared/formulas.ts`: `OliverBoxStats`型、`individualOffRtg`/`individualDefRtg`/
  `individualPointsProduced`（Dean Oliver方式、基本ボックススコアのみに依存）
- `shared/onCourt.ts`: `OnCourtInterval`は`ownPoss`/`oppPoss`のみ保持（PACE用）。
  `ownPts`/`oppPts`と`computeOnCourtRatings()`のoffRtg/defRtg/netRtgは削除済み

- `src/components/BoxscoreTable.tsx`: アドバンスドタブのORtg/DRtg/NetRtg/PACE列を選手行にも

  を置き換え）

## 18. アシストからの得点（2026-08-18）

15-6章で保留していたF4最後の項目（アシストからの得点）を実装した。アシストイベント
（`ActionCD1=12`）自体には、どの得点に紐づくかを示すタグが無い（PTSOFFTO等のように
`PlayText`を数えるだけでは算出できない）ため、「時間的近接性からの推測」に頼る前に、
より確実な方法（構造的なペアリング）が無いか事前にユーザーから調査を依頼された。

### 18-1. 構造的ペアリングの調査（実装前の事前検証）

`PlayByPlays`配列内でアシストイベントの直前に位置する、同一チーム・同一ピリオドの成功した
FG/FTイベントを構造的なペアとみなせないか（選手交代IN/OUTのペアリングと同じ考え方）を、
バックワードスキャン方式（アシストイベントから配列を1つずつ遡り、「管理系イベント」を
スキップしながら最初に見つかった成功イベントとペアリングする）で全10シーズン
（2016-17〜2025-26、計約24万件のアシストイベント）に対して検証した。

スキップする管理系イベントは、実データの遭遇順に発見した以下の集合:
`16`(バスケットカウント/アンドワンのマーカー)・`22`(パーソナル/シュートファウル)・
`84`/`85`(タイムアウト開始/終了)・`86`/`87`(選手交代IN/OUT)・`88`(タイムアウト)。

マッチ対象の得点イベントは当初`ActionCD1∈{1,3,4}`（3P/2P成功）のみを想定していたが、
実データ調査で**フリースロー成功（`7`）を含めないと一部のアシストが正しくペアリングできない**
ことが判明した。具体的には、シュートファウルでフリースローに切り替わった際、パスを出した
選手にアシストが記録され、その"アシスト"イベントが1本目と2本目のフリースローの間に
挿入されるという一貫したパターンを確認した（該当得点イベントの`PlayText`にも
「シュートファウル」タグが付いており、シュート試投がファウルに置き換わった状況と整合する。
2025-26シーズンでこのパターンは全アシストの約10.2%を占め、無視できない頻度だった）。
`7`を含めた最終形の一致率は以下の通り（`scripts/validate-assisted-scoring.ts`で再現可能）:

| シーズン | 一致率 |
|---|---|
| 2018-19、2019-20、2021-22、2022-23、2023-24、2024-25、2025-26 | 100.000% |
| 2017-18 | 99.9655% |
| 2016-17 | 99.9186% |
| 2020-21 | 99.8782%（実装時の内部整合性チェックで28→29件不一致に微修正。後述） |

残る不一致（全シーズン合計で約24万件中47件、0.02%）は個別に追跡済みで、選手交代IN/OUT
ペアリング検証（2-6章）と同様、既知のデータ品質問題（`RecordEditDateTime`が大きくずれた
記録修正・`No`値の重複等）に起因しており、ペアリングの考え方自体が誤っているわけではないと
判断した。この結果を先にユーザーへ報告し、「推測」ではなく選手交代IN/OUTと同じ「構造的に
決まったペアリング」として実装してよいとの確認を得た上で実装に進んだ。

### 18-2. 実装方針

- マッチに失敗したアシストイベント（0.02%）は無理に処理せず、得点との紐付け無しとして
  単純にスキップする（ユーザー指定の方針）
- 得点者視点で「アシストされた得点数」を2P/3P/FT別に保持する（`assisted2m`/`assisted3m`/
  `assistedFtm`）。UIには`AST2M`/`AST3M`/`ASTFTM`の3列と、`アシストされた得点の割合`
  （`AST%` = (assisted2m×2 + assisted3m×3 + assistedFtm×1) / PTS × 100）を追加した
- アシスト者-得点者のペア単位カウントも実装した（`buildAssistPairs()`）。「誰から誰への
  アシストが多いか」というペアランキングを将来作れるようにするためのデータ構造で、今回は
  ランキングUI自体は未実装（データを用意するところまで。ユーザー確認済み）
- 既存のASTボックススコア値（`sumCounts()`の`ast`）はそのまま変更しない。本機能は
  「アシストされた得点」という別の切り口の集計を追加するのみ

### 18-3. 検証

`scripts/validate-assisted-scoring.ts`で、選手単位（`byScorer`）の合計とペア単位（`pairs`）
の合計が一致するか（内部整合性）を確認した上で、実データでブラウザ確認した:
- 2025-26シーズン試合504728: 仙台89ERS・茨城ロボッツともチーム合計の`AST2M+AST3M+ASTFTM`が
  トラディショナルタブのAST値（各20）と完全一致（このシーズンはマッチ率100%のため）
- 個人単位のAST%計算も手動検証と一致（例: 船生誠也 1Q PTS=3・AST3M=1で AST%=100.0%）
- 期間トグル（1Q等）でも正しく再計算されることを確認
- 2016-17シーズン（legacy取得、マッチ率99.9186%）の試合でもエラー無く表示されることを確認
  （season制約は設けていない。ptsOffTov/DUNK等と同じ方針）

### 18-4. 実装ファイル

- `shared/assistedScoring.ts`: `computeAssistedScoring(playByPlays)`。バックワードスキャンで
  得点者単位（`byScorer`）・ペア単位（`pairs`）の2通りの集計を1回の走査で返す
- `src/lib/boxscoreAggregate.ts`: `BoxscoreCounts`に`assisted2m`/`assisted3m`/`assistedFtm`を

## 19. PPS・PPP（2026-08-18）

個人シーズンスタッツにPPS（Points Per Shot）・PPP（Points Per Possession）を追加した。
17章の個人ORtg（Dean Oliver方式）はボックススコア試合詳細ページ限定の実装だったが、今回
新たにシーズン合計値でも同じ計算式を再利用し、`statDefs.ts`（ランキング/比較/グロッサリー
ページ共通の定義）に反映した。

### 19-1. PPS

`PTS / FGA`。既存の`totals.pts`/`totals.fga`から`statDefs.ts`内で直接算出する（`aggregate.ts`
側の変更・再集計は不要）。出場時間の下限は設けていない（ユーザー指定通り。極端に試投数が
少ない選手ほど値が振れやすい点はPTS/FGAという定義上の性質としてそのまま許容する）。

### 19-2. PPP

個人ORtg（Dean Oliver方式、`shared/formulas.ts`の`individualOffRtg()`。17章でボックススコア
試合詳細ページ向けに実装・検証済みの式をそのまま再利用し、新しい計算式は作らない）を100で
割った値。ボックススコア側は1試合分の`BoxscoreCounts`を`OliverBoxStats`に変換して呼んでいたが、
今回は**シーズン合計の`StatTotals`**を同じ形に変換して渡す点が異なる（`scripts/aggregate.ts`の
`toOliverBoxFromTotals()`）。

- 選手個人・その選手の所属チーム・チームの対戦相手の3者分をそれぞれシーズン合計値で
  `individualOffRtg(player, team, opponent)`に渡す。移籍選手の所属チームはUsage%の既存実装と
  同様「直近所属チームで近似」する
- `individualOffRtg()`内部のガード（`MIN_MINUTES_FOR_INDIVIDUAL_RATING`、出場時間4分未満は
  undefined）もそのまま引き継がれる。試合単位では「1試合4分未満」のガードだったが、今回は
  同じ関数に**シーズン合計分**（`totals.min`）を渡すため、実質的には「シーズン合計出場時間
  4分未満」という、ごく一部の緊急出場選手のみに影響する弱いガードになる。ユーザーからも
  「同じ計算を再利用しているので当然同じ不安定性を引き継ぐはず」という前提で明示的に依頼
  されており、閾値を独自に再調整することはしていない
- シーズン合計値ベースであるため、試合単位の実装で問題になったqAST第2項の分母近傍0の
  不安定性（17-2節）は、母数が大きくなる分、発生しにくくなると見込まれる（実データでも
  極端な外れ値は確認されなかった。19-3節）

`shared/types.ts`の`PlayerAdvancedStats`に`ppp?: number`を追加（算出不能時はフィールド自体を
省略・undefinedにする。ボックススコアの「-」表示と同じ考え方）。`statDefs.ts`の`StatDef.value`
は`number`を返す契約のため、`value: (p) => p.advanced.ppp ?? 0`として未定義時は0扱いにし
（ランキングページで自然に最下部へ並ぶ）、`format`側で`p.advanced.ppp !== undefined ?
formatDecimal(...) : "-"`として表示のみ「-」にする。

### 19-3. 検証

`npm run aggregate`をB.PREMIER全11シーズン（2016-17〜2026-27。2026-27は試合0件で実質no-op）・
B.ONE 2025-26で再実行した。全ての完了済みシーズンで`players.json`の`ppp`フィールドが新規追加

## 21. チームカラー視認性バグの修正（2026-08-18）

### 21-1. 原因

`src/lib/color.ts`の輝度チェック自体（35〜220の範囲外を除外）は正しく機能していたが、
`src/lib/data.ts`の`fetchTeamColors()`が不合格時のフォールバック合成で`legibleAccentColor(...)
?? ""`という実装になっており、primary・secondary**両方**が不合格のチーム（アルティーリ千葉、
TeamID 2486。primary `#001030`＝輝度14.9、secondary `#000a1d`＝輝度9.2、いずれも
MIN_LUMINANCE=35を下回る）だけ、最終的に空文字列`""`が`TeamColors`に紛れ込んでいた。
呼び出し側の`homeColor ?? "var(--accent)"`という`??`（null合体）パターンは`null`/`undefined`
しか捕まえないため`""`をすり抜けさせ、CSS色値として無効な空文字列がそのまま渡っていた
（`accent ? {...} : undefined`というtruthyチェックパターンの呼び出し元は元々安全だった）。

### 21-2. 修正

- `shared/types.ts`の`TeamColors`を`{ primary: string; secondary: string }`から
  `{ primary?: string; secondary?: string }`に変更し、型レベルで「不合格時はフィールド自体が
  存在しない」ことを表現できるようにした
- `fetchTeamColors()`のサニタイズロジックを、primary・secondaryそれぞれ独立に
  `legibleAccentColor(...)`を評価し、不合格ならそのまま`undefined`（空文字列にフォールバック
  しない）にするよう修正。primaryが不合格でもsecondaryが合格ならprimaryにsecondaryを代入する
  という既存の代替ロジックは維持
- この1箇所の修正だけで、`??`パターン・truthyチェックパターンどちらの呼び出し元も自動的に
  安全になる（`undefined`はどちらのパターンでも正しく「値なし」として扱われるため）。
  呼び出し側（約20箇所）は変更していない

### 21-3. 全消費箇所の洗い出し（`??`パターンの脆弱性があった箇所）

`fetchTeamColors()`の戻り値を消費する全箇所をコードベース横断で確認した。`??`パターン

`LeadTrackerChart.tsx`(2箇所)・`KeyStatsSection.tsx`(2箇所)・`SubstitutionBarChart.tsx`

TeamDetailPageのヘッダー枠線など、残り約10箇所。21-2の根本修正により両パターンとも
安全になったため、個々の呼び出し元は変更していない。

### 21-4. 検証

## 23. 未開幕シーズンが「最新シーズン」に誤って解決される不具合の修正（2026-08-18）

`?season=`を付けずに素のURL（ブックマーク・外部リンク・ルート直アクセス等）で訪れると、
シーズン選択プルダウンが自動的に開幕前の2026-27シーズンになり、その状態で既存試合の
詳細ページを開くとFailed to fetch（実質404）になる不具合が報告され、原因調査の上で修正した。

### 23-1. 原因（2つの要因が組み合わさっていた）

1. **`scripts/aggregate.ts`の`regenerateSeasonsFile()`**が、`data/`配下のシーズン
   ディレクトリの**存在有無だけ**で`data/seasons.json`に載せており、実際に試合データが
   あるかを見ていなかった。`data/2026-27/`は`scrape-schedule.ts`の日程先行収集
   （開幕前から日程だけ取得する仕様）により既に存在しており、`npm run aggregate`を
   回すたびに0試合のまま`seasons.json`の末尾（文字列ソートで最新）に登録され続けていた
2. **`src/App.tsx`の`AppShell`**が`?season=`未指定時に`seasons.json`の末尾要素
   （＝1の不具合により2026-27）を「最新シーズン」としてフォールバック採用していたが、
   解決した値をURLへ書き戻していなかった。加えて**`src/components/SeasonLink.tsx`**の
   `withSeason()`は「現在のURLに`?season=`が無ければ何も付与しない」という仕様のため、
   一度`?season=`無しの状態に着地すると、以降のSeasonLink経由の遷移も`?season=`無しの
   まま連鎖し続ける（フォールバック値がURLに反映されないまま各ページで再解決され続ける）

この2つが組み合わさり、「?season=無しで着地→2026-27に誤ってフォールバック→以降の
遷移も?season=無しのまま→既存試合の`scheduleKey`に対して`data/2026-27/games/{key}.json`
を探しに行って失敗」という壊れ方をしていた。`git log`で確認したところ、
`data/seasons.json`への2026-27混入自体は今回のセッションで発生したものではなく、

## 24. チーム詳細ページ日程結果タブの`?season=`欠落バグ修正

### 24-1. 経緯・原因

23章の修正デプロイ後、「25-26シーズン表示中にチーム詳細ページの日程結果タブから
日付をクリックすると26-27シーズンに切り替わりエラーになる」との報告を受けたが、
本番URLで直接再現したところ再現しなかった（デプロイ前の古いキャッシュを見ていた
可能性が高い）。ただし調査の過程で、23章の修正とは独立した別のバグが実際に本番で
再現することを確認した。

`TeamDetailPage.tsx`の`TeamScheduleRowView`/`MaybeLink`（日程結果タブの日付・
対戦相手・スコア列のリンク）だけが、他の内部リンクが一貫して使っている
`SeasonLink`（現在の`?season=`を自動継承するラッパー、[[SeasonLink.tsx]]）ではなく、
素の`RouterLink`（react-router-dom）を使っており、`?season=`を一切付与していなかった。
このため「現在見ているシーズンが偶然latestSeasonと一致する場合のみ、23章の
フォールバック機構によって結果的に正しく見える」状態になっており、latestSeasonでは
ない過去シーズンのチーム詳細ページで日程結果タブの日付をクリックすると、
`scheduleKey`はそのシーズンのものなのにURLは`?season=`無し→latestSeasonへ
フォールバック、という組み合わせで404相当のFailed to fetchになることを実機で
確認した（例: 川崎ブレイブサンダース2020-21シーズン→2020-10-02の試合をクリック
→`?season=2025-26`に書き換わり`data/2025-26/games/5856.json.gz`が404）。

コードベース全体を検査し、同種の「素のRouterLink」使用箇所は他に2箇所のみ
（`PlayerDetailPage.tsx`のキャリアハイ試合リンク、`TeamDetailPage.tsx`のシーズン
履歴行リンク）だが、どちらも遷移先の`season`を明示的にクエリへ埋め込んでいるため
問題無いことを確認した。バグ箇所はこの日程結果タブの1箇所のみだった。

### 24-2. 修正

`TeamScheduleRowView`と`MaybeLink`内の`RouterLink`を、同ファイルで`Link`として
エイリアスされている`SeasonLink`に差し替えた。

## 25. ダーク/ライトモード手動トグル・ロゴ写真背景・チームカラー全落ちフォールバック

### 25-1. ダーク/ライトモード手動トグル

従来は`prefers-color-scheme`メディアクエリのみでOS設定に自動追従しており、
サイト側での手動切り替えは無かった。[src/lib/theme.ts](../src/lib/theme.ts)・
[src/components/ThemeToggle.tsx](../src/components/ThemeToggle.tsx)を新規作成し、
ヘッダー右上（シーズン選択の右）にトグルボタンを追加した。選択結果は
`localStorage`（キー`bleague-stats-theme`）に保存し、`<html>`要素の`data-theme`
属性（`"light"` / `"dark"`）で上書きする。`index.css`側は以下の3段構えで
優先順位を実装:

1. `:root` のデフォルト値（ライト）
2. `@media (prefers-color-scheme: dark)` 内の `:root:not([data-theme="light"])`
   ── 手動でライトに固定されていない限りOSのダーク設定に従う
3. `:root[data-theme="dark"]` ── 手動でダークを選んだ場合、OS設定に関わらず優先

初回読み込み時、Reactマウント前にOS設定と異なる手動選択が反映されるまでの
一瞬の描画切り替わり（FOUC）を防ぐため、`index.html`の`<head>`に同じキーを読む
同期スクリプトを追加し、CSS適用前に`data-theme`属性を確定させている
（テーマ切り替え・リロード後の維持をブラウザで確認済み）。

### 25-2. チームロゴ・選手写真コンテナの背景色

`.team-logo`（背景指定なし）、`.team-leader-photo`/`.player-cell-photo`/
`.player-photo`（`var(--header-bg)`、ダークモードでは暗いグレー）は、
ダークモードでロゴ・選手写真の透過部分がページ背景と同化して見づらかった。
新しいテーマ非依存の変数`--media-bg`（常に`#ffffff`固定、ダークモードでも
上書きしない）に統一し、テーマに関わらず常に白背景で表示するようにした。

### 25-3. チームカラー全落ちチームのフォールバック

23章以前の実装では、primary/secondaryとも視認性チェック不合格のチーム
（アルティーリ千葉等）は`undefined`のまま返し、各消費箇所で汎用アクセント
カラー`var(--accent)`（赤系）にフォールバックしていた。これだと「そのチーム
自身の色であるかのように誤解を招く」ため、[src/lib/color.ts](../src/lib/color.ts)に
`MONO_FALLBACK_COLOR = "var(--fg)"`を追加し、`fetchTeamColors()`
（[src/lib/data.ts](../src/lib/data.ts)）で両方不合格時にこちらを使うよう変更した。
`var(--fg)`は本文の文字色と同じ変数のため、25-1のテーマ切り替えにも自動で
追従する（ライト: 黒系、ダーク: 白系）。個々の消費箇所を変更する必要は無く、
`fetchTeamColors()`一箇所の変更で全消費箇所に反映される。

### 25-4. 検証
